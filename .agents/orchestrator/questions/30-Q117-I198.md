## 1. Is it ok that `i64 3 ^ f64 2.0` is refused, as `i64 3 + f64 2.0` already is?
**Decided by me:** refused · **Why:** a number may convert where it is not written only when nothing is lost (your Q83 and Q63)

---

Issue #198 (one conversion step wherever a value meets a number type it is not) makes the library's `^` follow that rule. `^` is written in Logos, in `identities/power.logos`. Today it converts its left side to the right side's type without checking, so:

```
x := i64 3, y := f64 2.0, x ^ y      # today 9.0; now refused
x := i32 3, y := f32 0.5, x ^ y      # today 1.7320508; now refused
x := i32 3, y := f64 0.5, x ^ y      # still 1.7320508: every i32 fits in an f64
```

An `f64` cannot hold every `i64`, so `x ^ y` could lose part of `x` where you never wrote `lossy`. `+` refuses the same pair for that reason. You write the loss yourself: `f64 lossy (x) ^ y`.

## 2. Is it ok that a function's bare parameter is refused when a type's own `parse` reads it, until #216?
**Decided by me:** refused for now · **Why:** a field takes a value of unknown type only where its type says so (›Deferral is authored, and unfinished work is visible‹)

---

A bare parameter is one written without a type, as `b` in `fn (b)`. Its type is known only when the function is called. `pt` below is a type whose own `parse` reads the value to its left:

```
g := fn (b) -> i64 ( b pt ), g(i64 3)      # dev gave 6; now refused
g := fn (b) -> i64 ( b pt ), g(f64 3.5)    # dev gave -9216616637413720064
```

Dev let the value in unchecked, which is how the second line printed a wrong number. `b + b` and `h(b)` are already refused the same way. The first line works again once #216 builds a function's body once for each set of argument types.
