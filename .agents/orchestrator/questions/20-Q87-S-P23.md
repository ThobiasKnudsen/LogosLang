## What is wrong, in plain words

Some bodies are written in one place and built later. A type's `run` body is built when the first node of that type appears. A `type (…)` written inside a loop or a function is built each time that body runs. Building a body means parsing its text into graph nodes.

Where such a body is written, the seed keeps only its text and its scope. Everything else happens at the build. That causes two kinds of failure.

**1. The body's names are looked up at the build, so it sees a name declared after it.** On dev 83e3f97, interpreted, `u`'s `run` body declares its own `z`, and the program declares another `z` after `u`:

```logos
u := type ( a := ?, output_type := type ?, share run = ( z := a, f64(z) ), share parse_rank = 60, share parse = ( tape[0]:type = u, tape[0].a = tape[1], tape[0].output_type = f64, tape.remove(1), tape.is_constructed[0] = true ) ), z := i32 0, x := i32 3, print «{u x}»
```

It prints `error: z is already declared and still in scope`, exit 1. Without `z := i32 0, ` it prints `3.0`. A `type (…)` in a loop fails the same way.

**2. A body that needs another body builds that one in the middle of its own build.** If `t0`'s `run` body holds a node of type `t1`, building `t0`'s body builds `t1`'s body inside it, and so on down a chain, all on one Rust call stack. A chain of 18 types, each `run` body 1,990 brackets deep around a node of the next type:

```logos
t1 := type ( a := i32 ?, share run = ( ((( … 1,990 deep … 3 t2 … ))) ), share parse_rank = *.parse_rank + 1, share parse = ( … ) ), … , 3 t0
```

With 17 types it prints `leaf`. With 18 the program dies with `thread has overflowed its stack` (an abort), not with a Logos error. A single wall of 2,500 brackets gives the checked error "scopes nested deeper than 2000", but that count starts again at 0 inside every body built later, so a chain never reaches it.

The why agents found the causes under these two, among them:
- DESIGN does not say which line a later-built body reads its names at (question 1).
- DESIGN does not say what a node of a type with a `run` gives when the type declares no `output_type`, and the seed only learns it by building the body (question 2).
- DESIGN has no rule on how deep nesting may go (question 3).

## 1. Where does a body that is built later read its names?
**Decision:** which line a later-built body's names belong to · **Recommended:** (a) · **Why:** DESIGN already reads names this way for a function's body

---

DESIGN says two things here. ›A binding's fields are read at elaboration, at the line of the read; running code never reads a binding‹ says a read is answered "when the node holding the read is built, from the binding as it stands at that line". For a body built later, that is the build. Its Why says "A reader at an earlier line must not see a later state, so the answer is fixed where the read is built", which reads as where the body is written. And ›A call is a use of every outer name the callee's body reads‹ says: "A body resolves outside names when parsed … the body's `n` is the old, ended name. To read the new name, declare the function again after it."

An example where the two readings differ:

```logos
x := i32 5, t := type ( a := i32 ?, share run = ( x + a ), … ), free x, x := f64 1, 3 t
```

Read where the body is written, its `x` is the first `x`, which is freed, so `3 t` is the dead-name error. Read where it is built, it is the new `f64` `x`.

- (a) **Where it is written.** A body built later looks up every name once, where it is written, in the part of it built there. Its build never looks up a name again. The first program above prints `3.0`, since the later `z` did not exist where the `run` body is written.
- (b) **Where it is built, but only names alive where it was written.** Each line of a body gets a number, a name's life becomes two numbers, and every lookup at a build checks that the name's life covers the place the body was written. This also fixes the first program. In the example above, `3 t` reads the new `x`, which goes against "the body's `n` is the old, ended name".

Recommended: (a), because it is what ›A call is a use…‹ already says for a function's body, and the build then has nothing left to look up.

The words (a) adds under ›A binding's fields are read at elaboration, at the line of the read; running code never reads a binding‹:

> - **Ruled (<the date of your answer>, Thobias, Q87):** a body written in one place and built in another, a `fn` body, a type's `run` body or a `type (…)` in a body, reads every name and every binding field as it stood where the body is written, and its build looks up no name again: `u := type ( a := ?, …, share run = ( z := a, f64(z) ), … ), z := i32 0, x := i32 3, print «{u x}»` prints `3.0`, since the later `z` did not exist where the `run` body is written. **Why:** <your words>.

## 2. What does a node of a type with a `run` give when the type declares no `output_type`?
**Decision:** what such a node gives back · **Recommended:** (a) · **Why:** it is known without building the body, which question 3 needs

---

In the chain above, every `t1`, `t2`, … has a `run` but no `output_type`. DESIGN does not say what `3 t1` gives back. Today the seed gives nothing. On 2 October (Q-59, Q-61) you ruled that `:=`, `return`, `while` and the other statement words have no `output_type` and give their line nothing.

- (a) **Nothing.** A type gives a value only when it says what that value is, with `output_type`. Over such a type `t`, `y := 3 t` is the error of binding nothing. The parse knows this as soon as it places the node, without building the body.
- (b) **What its `run` body's last line gives.** This is how you ruled on 8 October (Q72) that a block's value is worked out. But the last line's type is only known once the body is built for this node, so every such node used as a value forces a build inside the build that uses it, which is exactly the chain's crash.

Recommended: (a), because it is the statement-word rule applied to every type, and it is what lets question 3's fix place a node before its body is built.

The words (a) adds under ›A node's output type is per node, and its parse writes it‹:

> - **Ruled (<the date of your answer>, Thobias, Q87):** a node of a type with a `run` gives nothing when its type declares no `output_type`, as the statement words do; over such a type `t`, `y := 3 t` is the error of binding nothing. **Why:** <your words>.

## 3. How should a chain of bodies that build each other behave?
**Decision:** how the chain's crash is fixed · **Recommended:** (a) · **Why:** the chain runs, and a deep wall of brackets still gets a Logos error

---

- (a) **Build after, not inside, with a depth rule as a safety net.** When a body being built places a node of a type whose `run` body is not built yet, the node is placed at once: its output type comes from question 2, and the outer names its body reads come from question 1. Its body goes on a list and is built as soon as the build that placed it ends, still before anything runs. The chain then runs at any length. Separately, the 2,000-bracket limit becomes a rule and counts across bodies too, so a 2,500-deep wall is still a Logos error. An error inside `t1`'s body then shows just after `t0`'s body is built, not in the middle of it. This needs (a) in question 1 and (a) in question 2.
- (b) **Only the depth rule.** Brackets are counted across every body being built. The 18-type chain gives the Logos error "scopes nested deeper than 2000" instead of crashing, but it still cannot run. This is small, about 30 lines.
- (c) **Nesting in memory instead of on the Rust stack.** A constructor may stop at an inner bracket and continue at its closing bracket, so depth is limited only by memory. This changes ›A constructor's outcome is read off its own cell; no holding, no re-invocation‹ and rewrites the driver and every constructor, far more than this needs.

Recommended: (a), because nothing builds inside a build any more, and the depth rule still turns a too-deep wall of brackets into an error instead of a crash.

The words (a) adds. Under ›A generic function body is lexed once and built once per set of field types‹:

> - **Ruled (<the date of your answer>, Thobias, Q87):** a body that waits for a node is built after the build that placed the node ends, never inside it. The node is placed first, with its output type and the outer names its body reads, both known before that body is built. **Why:** <your words>.

Under ›The scope's constructor is the driver‹:

> - **Ruled (<the date of your answer>, Thobias, Q87):** the drive's nesting has a limit, set by the implementation (the seed's is 2,000). Crossing it is a checked error at the bracket that crosses it, never a crash. The count is every bracket open in the whole pass at that moment, inside a body being built too. **Why:** <your words>.
