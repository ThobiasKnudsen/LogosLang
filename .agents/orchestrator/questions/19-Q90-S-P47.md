## Your comments on the last question, answered

This follows Q84, about the field reads inside a type's `parse` (the Logos code that runs when the type's name appears, and builds the node for that appearance; `tape[0]` is the node it builds).

**"What is a local of a function?"** I meant a name declared inside a function: its parameters and the names its body declares. In `f := fn (x := i32 ?) -> i32 ( y := i32 5, x + y )`, both `x` and `y` are such names. Each call of `f` has its own `x` and `y`, so they have a value only while a call of `f` runs. I avoid the word "local" below. Your question about a bad-word list is question 2.

**The line `tape[0] = tape[0].m`.** It replaces the node being built with the node held in its field `m`. So the appearance `q (1, 2, 3)` becomes what `m` holds, and the `q` node itself is dropped. It is odd, but it is only there so that the program prints what `m` holds. It should work, and it does under both options below: a tape cell takes any node, so this line needs no type for `m`.

**"If there is a `?` which makes the type unknown, then it should not parse at that point."** That is option (a) below. You asked what state would make the line parsable later. It is the moment the parse reaches that line, at an appearance of the type. By then the parse has written the field, so the field holds a node whose type is known. In the second program, when `q (1, 2, 3)` appears, the parse first writes `tape[0].n = tape[1].dyads.size`, which puts the `u64` number 3 into `n`. When it then reaches `tape[0].m = tape[0].n * 2`, `n` is known to be a `u64`, and the line can be parsed.

**How a waiting line is kept, and how you know it is not parsed.** The line stays as its lexed cells, the same form `lex «…»` gives. The seed already keeps a type's `run` body this way: lexed where it is written, and built when the first node of the type appears. The tape's own `is_constructed` list already marks which cells are built (›`is_constructed` is the tape's own list, read `tape.is_constructed[k]`‹). So this fix needs no new bit. A parsed-or-not bit in every pointer would be a separate and much larger question.

**"In most of these cases minting should be used instead."** Minting alone does not solve this one. DESIGN says a type's parse "runs before the mint is made" and "chooses the mint from its operands' types" (›A type with a `run` whose field is `?` mints too, so its `run` body is parsed once per mint‹). The parse body is built once, where the type is defined, before any mint exists. So when the build reaches `tape[0].n * 2`, it still cannot know which mint `tape[0]` will be, unless the parse has checked the type at that point. Your own example, "mint for when n.type is u64 and for when its u32", is such a check, one branch per type. That is option (b) below. Inside each branch the type is known, so the branch can be parsed where it is written, and that branch is also where the parse would choose its mint.

**The third program** (`.type` of a `?` field, which today gives "this read does not fit the node's type"). `.type` always gives a `type`, whatever the field holds, so the line has a known type and can be parsed where it is written. It works under both options, and prints `rational_number`, the type of the plain number `3`.

**The first program** (the one that printed a random number inside a function) prints `8` under both options. Its fields are declared `i32`, so no `?` is involved.

## 1. A field declared `?`, used in the parse before its type is known
**Decision:** what the parse does with a line that needs the type of a `?` field · **Recommended:** (b) · **Why:** it is your "mint per type" done with the check a parse already uses, so every type is known where the body is written

---

The second program today:

```logos
q := type ( n := ?, m := ?, share parse_rank = 60, share parse = ( tape[0].type = q, tape[0].n = tape[1].dyads.size, tape[0].m = tape[0].n * 2, tape[0] = tape[0].m, tape.remove(1), tape.is_constructed[0] = true ) ), q (1, 2, 3)
```

It gives `error: this operator cannot compute over these operands`, because `n` is `?` and `*` needs to know what it multiplies.

- (a) **Wait: the line is parsed when the parse reaches it.** A line of a parse body that needs the type of a `?` field is kept lexed where the type is defined, and is parsed when the parse reaches it at an appearance, once the field holds its node. The second program prints `6` as written. The third prints `rational_number`, and the first prints `8`. The costs: the line is parsed again at every appearance of the type, so a type used often parses more slowly. A mistake in the line shows only where the type is used, not where it is defined. And the seed cannot yet build one line of a body later, so this fix would wait for that unfinished work. This would be recorded at ›A generic function body is lexed once and built once per set of field types‹ as:

  > **Ruled (<the date of your answer>, Thobias, <this question's id>):** the rule holds for a type's `parse` body too. A line of it that needs the type of a `?` field of the node being built is kept lexed where it is written, and is parsed when the parse reaches it at an appearance, once the field holds its node; it is parsed again at each appearance. `.type` needs no type and is parsed where it is written. Inside a parse, `tape[0].f` is the node its slot holds, never run there; written into the node, it and anything built over it are kept as graph and run when the node runs, so `tape[0].rhs = tape[0].lhs` copies the operand node. **Why:** <your words>.

- (b) **Check first: one branch per type, as a mint is chosen.** The parse body is built once, where the type is defined. A `?` field has no type there until a check gives it one, the same check the parse already uses on a tape cell. The second program is written with the check, and then prints `6`:

  ```logos
  q := type ( n := ?, m := ?, share parse_rank = 60, share parse = ( tape[0].type = q, tape[0].n = tape[1].dyads.size, if tape[0].n.type ⊆ u64 ( tape[0].m = tape[0].n * 2 ), tape[0] = tape[0].m, tape.remove(1), tape.is_constructed[0] = true ) ), q (1, 2, 3)
  ```

  A second branch, `if tape[0].n.type ⊆ u32 ( … )`, would handle `u32`, and each branch is where a mint for that type would be chosen. As written, without a check, the second program is an error where `q` is defined. The third prints `rational_number`, and the first prints `8`. Nothing is parsed again at each appearance, and nothing waits for other work. This would be recorded at ›A tape read checked against a number type reads as that number‹ as:

  > **Ruled (<the date of your answer>, Thobias, <this question's id>):** inside a parse, a field of the node being built, `tape[0].f`, is the node its slot holds, never run there. Its type is the field's declared type. A `?` field has no type there until a check gives it one, as a tape cell's check does: `if tape[0].n.type ⊆ u64 ( tape[0].m = tape[0].n * 2 )`; outside such a check, a use that needs its type is refused where the type is defined, and `.type`, which needs none, reads the type of the node the field holds. Written into the node, the field and anything built over it are kept as graph and run when the node runs, so `tape[0].rhs = tape[0].lhs` copies the operand node. Read for its value while the parse runs, only a constant gives one; anything else is the checked error. **Why:** <your words>.

Recommended: (b), because it is the branch per type you described for minting, built with the check a parse already uses on its tape cells, so every type is known where the body is written and nothing is parsed twice.

## Decided
These are my own decisions. Answer "ok" to accept them, or write what you want instead.
- **A call remembers which function it is a call of.** When `f(4)` runs, the seed sets aside memory for that one call, and `x` lives there. Today, when the seed reads `x`, it looks in whichever call is running at that moment, even when that call is not a call of `f`. That is how the first program read the wrong memory: the parse's own call was running, not a call of `f`. The fix makes each call remember which function it is a call of. A read of `x` then checks that the running call is a call of `f`. If it is not, the program stops with the error the seed already has for this case ("a function's local was read outside any call"), instead of giving a random number or crashing. It costs one comparison per such read in the interpreter, and nothing in compiled code. It rests on DESIGN's rule that a function's names are read in "a call's frame" (›A scope lays out its declarations; a use reaches the offset through its binding‹), so it adds no new rule.
- **The option you pick replaces an older proposal on GitHub issue 203.** That proposal said a parse should run the node held in the field, which is what printed the random number. No new issue is opened.
