Issue #234 (one way to read a scope's lines) lets one REPL line hold several items, so a line can import a file and then fail. Its reviewer found that the branch then frees what the file holds but still counts the file as loaded, so the next `import` hands back freed values:

```
» import ./held.logos, error «boom»     # held.logos: pub h := bag(9)
freed 9
<repl>: run error: boom
» import ./held.logos
» h.n
9          # reads a bag that was already freed
```

- **Decided:** the imported file belongs to the session, not to the line. The failure takes the line's own names back out, as before, but the file stays loaded and alive until the session ends. A later `import ./held.logos` hands back the same file without running it again, `h.n` gives `9` from a live bag, and `freed 9` prints when the session ends.
- **Why:** your rules already say so. ›Importing is dropping the text there, wrapped in its own scope‹: "A file loads **once per run**; all importers share the one loaded scope", and your ruling of 28 September there: "it lives separately". "A failed line rolls its declarations back out of the name index, leaving no trace" speaks of the name index, which this keeps clean. The other choice, forgetting the file so it loads again, would run its top level twice in one session, where the command line runs it once.
- **What it costs:** a fix round on #234 before it merges, so the line's failure frees only the line's own values.
