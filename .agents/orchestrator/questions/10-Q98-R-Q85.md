## 1. What facts Rust's new borrow checker rests on
**Decision:** none, this is a reply · **Recommended:** answer "ok", or ask on · **Why:** you asked this in Q85 and got no reply

---

Rust's new borrow checker is Polonius. Its first part has been on Rust's nightly build since 4 August 2026, and is meant to be stable before 2027. Its facts (`polonius-engine/src/facts.rs`):

- **Points and edges:** each step of a function is a point; an edge says which point can follow which. An `if` is two edges.
- **Loans:** a borrow `&x` taken at a point, and the points where it may still be used.
- **Subsets:** a reference copied into another passes its loans on.
- **Kills:** a write to a borrowed place ends its loans.
- **Liveness and moves:** where each name or path (`x.f`) is used, written, moved and dropped.
- **Signatures:** the lifetimes a function's signature names. Rust checks each function alone, reading only the signatures of what it calls.

An error is a rule over the facts: a loan broken where it is still in use.

Logos already has this list, in DESIGN.md ›The checker reads a fact base the graph provides; the rules over it are user-definable‹. Subsets and signatures have no fact of their own there, and signatures matter for speed: there a call's edge goes into the called function's body.

On branches: Rust stores nothing per branch; the rules join the paths. A value moved in one arm is "maybe moved" after the `if`, so a later use is an error. DESIGN does the same: a loan taken in an arm counts on every path.

## 2. Is an output_type per `if` what makes Logos fast again?
**Decision:** none, this is a reply · **Recommended:** answer "ok", or ask on · **Why:** you asked this in Q85; your Q89 answer depended on it

---

No. On issue 82's branch (commit fe96f57, not on `dev` yet) speed came back without it, as you wished in Q89. There a function says in its result that it hands on what it made, and a call reads that instead of walking the other body, as Rust reads a signature: `h1 := fn () -> own @i32 ( if (c == 1) (h0()) else (h0()) )`.

Measured there: a chain of 20 functions reads in 7.0 ms (before: 22 took 1.01 s, doubling per function). An `if` with 2,000 arms takes 37.2 ms.

But a much longer chain is still slow, on `dev` too: 83 ms at 500 functions, 404 ms at 1,000, 2.6 s at 2,000, five to six times longer each time the chain doubles. Review round 6 found it today. It is older than issue 82, and it is now problem P139; its why agents come later.

## 3. Why I recommended merging with the slow code
**Decision:** none, this is a reply · **Recommended:** answer "ok", or ask on · **Why:** you asked "didnt you recognize this as bad code?" and got no reply

---

I saw it as slow, not as wrong. No rule said that reading a program must take time in step with its size, so I weighed it like any other problem found in a review: the slow shape needed a long chain of functions calling each other in both arms, and holding issue 82 held many other fixes. You were right that the slowness pointed at a wrong solution.

What changed that night, so a review now stops such code:
- DESIGN.md got the rule ›Reading a program takes time in step with its size; no walk runs once per path‹, so slowness is a defect reviewers check against.
- Every review round runs speed probes (`.agents/orchestrator/AGENTS.md`), at two sizes, on the branch and on `dev`.
- Every agent runs at effort xhigh, as you chose.

The probes have a limit: they use 10 and 20 functions, and P139 shows only from about 500. Making them catch it goes with P139's fix.
