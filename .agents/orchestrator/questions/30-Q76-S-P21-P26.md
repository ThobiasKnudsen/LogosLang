## The two root causes, in plain words

**W54: `type.logos` does not say what a type's record holds.** `identities/type.logos` is the file where `type` says what every type holds. Today it names five fields:

```
type := type (
    parse_rank := f64 ?
    associativity := ?
    parse := parse ?
    run := run ?
    free := free ?
    …
)
```

A type's record in the seed holds more than that. It also holds `scope`, `fields`, `size_bytes`, the cached pointer type `@T`, an `extent` reader, and a **kind byte**. The kind byte is a small number at the start of every type's record, picked from a fixed list in Rust (`i32` is 2, `f64` is 9, and so on). These extra parts exist only in Rust, in `src/identities/meta.rs`, as byte positions chosen per kind byte. DESIGN asks for the opposite. ›Still to be written in type.logos; reflection of fields is open‹ says: "Every field under the `type` scope must be expressed there". The same rule also leaves open what a type shows about its fields. You can see the gap on `type` itself:

```
type.size_bytes          error: this read does not fit the node's type
type.scope               error: this read does not fit the node's type
type.parse_rank          92.0      (read from a Rust byte position)
```

**W49: the seed has no backend identity.** A backend is what turns Logos into machine code, today Cranelift. DESIGN says a backend is an ordinary identity that carries its own rules (›Backends are identities, and lowering is keyed by them‹: "Nothing per identity may hard-code one backend"). The seed has no backend identity. It has one global Rust table from each identity straight to Cranelift code. So the rule "`+` over two `i32`s is the machine operation `add_i32`" has nowhere to live, and it stays in Rust inside `+`'s parse, which looks the operation up **by the kind byte**.

## The problem both explain

P26: a comparison adds to a number.

```
x := i32 1, (x == 1) + 1
2
```

It should be refused, as `true + 1` already is ("this operator cannot compute over these operands"), because a comparison gives a `bool`. The same root cause W54 also explains two more problems:

```
x := i32 1, a := x == 1, a                      prints 1, should print true      (P21)
x := i32 1, mut a := i32 0, a = x == 1, a      prints 1, should be refused     (P27)
```

The chain behind them is this. Because `type.logos` declares no shape for a record, Rust picks every record's shape by its kind byte. So the kind byte is the only thing in the seed that says what a type is. The fixed list has no entry for `bool`, so `bool` borrows `i32`'s entry, and a comparison is then treated as an `i32`. `+` picks its machine operation by that same byte, so it happily adds the comparison to `1`.

**Already chosen, and it fixes all three problems sooner:** S1, issue #82 ("every built-in node carries the type it gives back"). Once #82 lands, a comparison says by itself that it gives a `bool`, and nobody guesses from the kind byte. So nothing below is needed to fix P21, P26 or P27. The questions below are about removing the two root causes themselves.

## 1. Which fix for W54 (what a type's record holds)?
**Decision:** how far the fix for W54 goes · **Recommended:** (a) · **Why:** it removes the root cause, and its first slice is just the rule

---

- (a) **S23, the whole fix.** `type.logos` declares every field a type's record holds, and the record holds nothing else. The fields are `parse_rank`, `associativity`, `parse`, `run`, `free`, `print` (already ruled in #174), `scope`, `fields`, `size_bytes` and `extent`. What only one kind of type needs becomes a `share` member in that type's own body: a pointer type's `pointee`, an operator's `arity` and `roles`. The cached `@T` leaves the record, and `@` keeps its own list of pointer types, as `array` keeps one type per element type. Rust then knows only the layout of `type` itself, which DESIGN allows (›The dyad describes itself down to one fixed point‹: "whose layout is the seed's only built-in knowledge"), and a test checks that layout against `type.logos` field by field. Afterwards `i32.size_bytes` is `u64 4` because `i32` fills it in, and `bool` is `bool` everywhere. It comes in four slices: (1) the rule and `type.logos`; (2) every type fills `size_bytes`, `scope` and `fields`, and the readers go through them; (3) the extras per kind become `share` members, and `@T` moves to `@`; (4) the kind byte goes (#101, the open issue about that fixed list). It is big: about 70 places in Rust read the kind byte or the record's byte positions, so it runs alone in `src/identities`.
- (b) **S24, the rule only, for now.** Write the rule and complete `type.logos`, and leave the seed on its Rust byte positions. This is cheap and touches no code. But the seed keeps a second copy of the shape that nothing checks, and the root cause stays. It is the same as slice 1 of (a).

Recommended: (a), started with its slice 1, so the rule lands now and the seed slices follow after #82.

## 2. What does `t.fields` give? (DESIGN has this open)
**Decision:** what reading a type's fields from Logos returns · **Recommended:** (a) · **Why:** `size_bytes` already needs this list, and it is your website loop

---

Your website's showcase walks a type's fields. For example:

```
pt := type ( a := i32 ?, b := i64 ? )
pt.fields.length                 u64 2
for f in pt.fields ( print «{f:name} {f.type}» )
a i32
b i64
```

- (a) **The list of the type's per-value fields, as their bindings, in the order they are written.** `share` members are not in it. `f:name` is a field's name and `f.type` is its type. This fits ›Field names live in the shared name index, not on the type‹, because the list points at the bindings and copies no names. It is also exactly the list that `size_bytes` adds up (›`.size_bytes` is a `u64`‹).
- (b) **Leave it open.** `type.logos` still declares `fields`, so the record has a place for it, but reading it from Logos waits.

Recommended: (a), because `size_bytes` already needs this list to exist, and the walk is what you wanted on the website.

## 3. Which fix for W49 (no backend identity)?
**Decision:** when and how a backend becomes an identity · **Recommended:** (d) · **Why:** nothing waits on W49 once #82 lands, and (a) would build on code #164 deletes

---

Two terms first. A **machine operation** is one instruction the computer runs, such as `add_i32` (add two 32-bit integers) or `fadd_f64` (add two 64-bit floats). A **mint** is the type an operator makes for one set of operand types: `+` over two `i32`s is one mint of `+`, and `+` over two `f64`s is another. The **Logos IR** is a small typed language between the Logos graph and the machine, planned in #164 ("one definition per identity, then a small typed Logos IR read by an IR interpreter and by Cranelift").

- (a) **S25, a backend identity now.** Make a `cranelift` backend identity in the core. Its record holds the lowering rules, the 23 places that fill the Rust table register on it instead, and `f.compile()` goes through the backend it is given. This follows the rule's letter today. But with one backend it is mostly a rename, and #164 rewrites the same code later.
- (b) **S26, machine operations chosen by rules.** `add_i32` and `fadd_f64` become identities, and one rule per mint of `+` picks its machine operation. The Rust lookup by kind byte goes. A new number type is then new rules, never an edit to `+`. This is the deep fix, but it is the same question as #152 ("how an operation such as `=`, `==` or `+` is defined for its operand types"), which you left open on 26 September with "nothing concluded".
- (c) **S27, the backend becomes an identity together with the Logos IR (#164).** Every identity is turned into the IR once, the same for every backend, and the `cranelift` backend identity carries the rules from IR operations to machine code. Nothing is built on today's Rust table. W49 stays open until #164, which comes late in your order.
- (d) **(c) now as the plan, and (b) later as its own fix**, once #152 is ruled.

Recommended: (d). #82 removes P26, so nothing is lost by waiting, and (b) belongs to #152's open question.

Only if you take (b), two more points need your answer. First: does the interpreter use the same rules as the backend? For example, `x := i32 1, x + 2` with no `compile` at all still needs `+` over `i32` to mean `add_i32`. Recommended: yes, one set of rules that no backend owns, and a backend only says how to emit each machine operation; two copies would be the root cause W4 ("every meaning written twice, once to run and once to compile"). Second: does (b) wait for #152? Recommended: yes, since you asked on 26 September that nothing be concluded there.

## 4. The kind byte: when may it go?
**Decision:** whether S23's last slice waits for (b) or puts a Rust stand-in in its place · **Recommended:** (a) · **Why:** #82 already fixes the problems, and a stand-in is a second mechanism

---

This is where your answers to 1 and 3 must agree. The kind byte does two jobs today. It tells Rust what shape a type's record has, which S23 replaces with the fields `type.logos` declares. And it tells `+` which machine operation to use: `+` over `i32` looks up `add_i32` by the byte. Slice 4 of S23 removes the byte, so the second job must go somewhere else first. DESIGN already says where. ›Which machine operation an operator is (`+` over `i32` → `add_i32`) is a lowering rule‹, as you ruled on 2 October (Q-61), says that a rule per mint picks the operation the first time a node of that mint runs or is compiled, and keeps it on the mint. That rule is S26, option (b) of question 3.

- (a) **S23's slice 4 waits for S26.** Slices 1 to 3 go ahead. The byte is removed only after `+` picks its operation by the rule per mint. If you take (d) in question 3, that is after #152 is ruled. If you take only (a) or (c), the byte stays until #164.
- (b) **S23's slice 4 puts a stand-in in Rust.** `+` checks the type itself (is it `i32`? is it `f64`?) instead of the byte, using Rust's list of the ten number types, until S26 replaces it. The byte goes sooner, but a hand-kept list of types stays in Rust in the meantime.

Recommended: (a). #82 already fixes P21, P26 and P27, so nothing waits on the byte, and the stand-in would be a second mechanism that S26 deletes.
