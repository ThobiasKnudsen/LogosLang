## What this is about

Issue #66: `move g.b` ends the field `g.b` while `g` lives on. Its first slice, the parse errors, is being built now: after `y := move g.b`, the program `g.b`, `g`, `move g` and `f(g)` are parse errors, while `g.items[0]` still reads. The second slice, what `g`'s `free` runs at the end of the scope, needs your answers. The example type (from `tests/cli.rs`):

```
bagged := type ( mut items := own t ?, mut b := own boxed ?, share free = ( print «bag», free items, free b ) )
g := bag (), y := move g.b
```

## 1. Does `move g.b` still write NULL into the field?
**Decision:** what the move leaves in `g.b` · **Recommended:** (a) · **Why:** the same rule a name follows, and only a failing line ever reads it

---

Two rules read differently. ›`move` and `free` take a field path too‹: "At scope exit p's free **skips f** … no type writes an "empty" value." ›`free` and `move` end a name; no drop flag‹: "`free` and `move` write NULL into the place they end, and a line that fails frees every place … that is not NULL".

- (a) **Yes.** On a normal path `g`'s `free` leaves `free b` out because the parse knows; nothing checks. If a line fails after the move, the cleanup frees `g` whole, and the NULL keeps it from freeing the box twice. "No type writes an empty value" then means: no type needs an empty form its `free` looks for.
- (b) **No.** Then a failing line after the move frees the box twice, unless a new rule says otherwise.

## 2. Which lines of the `free` belong to the field `b`?
**Decision:** what is left out of `g`'s `free` after `move g.b` · **Recommended:** (a) · **Why:** exact, and `free` is the one way a field is torn down

---

- (a) **Only the line `free b` itself.** `print «bag»` and `free items` still run. A line that reads `b` another way, like `print «{b.size}»`, runs too and fails at the scope's end.
- (b) **Every line that names `b`.** A line naming `b` and another owning field, like `free_both(items, b)`, then makes `move g.b` an error, since leaving it out leaks `items`.

## 3. Paths that do not start at a name
**Decision:** what happens to a move the parse cannot follow back to a name · **Recommended:** (a) · **Why:** they work today, and only these keep a check at run

---

```
pp := &x, b := move pp@.p                      # through a pointer
l := array bagged [bag ()], y := move l[0].b   # through an array element
y := move g.b.p                                # two fields deep
share s := fn () -> i32 ( free p, 2 )          # a share function freeing its own value's field
```

- (a) **Keep them working as today:** for these alone the owner's `free` meets the empty field and frees nothing there, a check at run kept only where the parse cannot know. Recorded as an Open line.
- (b) **Refuse them** until a rule covers them, as Rust refuses moving out of a borrow. Tests that run today break.

## 4. May `g := …` follow `move g.b`?
**Decision:** whether a new declaration of `g` is allowed after a partial move · **Recommended:** (a) · **Why:** `g`'s other fields are still freed at the scope's end, so the old place cannot just be dropped

---

›A dead name takes nothing; only `:=` may follow‹ allows `:=` after a name dies, because "nothing runs for the old place at scope exit". After `move g.b`, `g` is dead as a whole, but its other fields still run at scope exit.

- (a) **Refused until the scope ends,** as slice 1 does now.
- (b) **Allowed,** with the old place's other fields freed at the scope's end under the old binding.
