## What this is about

Three files hold the rules agents follow:

- `~/.claude/CLAUDE.md` is your global instruction file. Every Claude session on this machine reads it, also sessions in repos with no orchestrator.
- `~/.claude/skills/orchestrate/agent-agnostic-prompt.md` holds "the rules every agent follows in every repo". Your CLAUDE.md imports it, so every session reads it too, and the orchestrator also pastes it into every prompt it gives an agent.
- `~/.claude/skills/orchestrate/every-prompt.md` holds the rules for the agents an orchestrator starts. Only those agents get it. It has blanks such as `{{ORCH}}`, which the script fills in with the repo's names.

The trouble: agent-agnostic-prompt.md is meant for every session, but it is written in the orchestrator's words, and your CLAUDE.md says the opposite to the same session. Two examples:

```
agent-agnostic-prompt.md  A problem your task does not cover is reported as `FOUND` and never filed.
CLAUDE.md                 In a repo without an orchestrator, a root cause is filed as an issue with the `root-cause` label
```

```
agent-agnostic-prompt.md  Only the orchestrator writes the ruling document and its history file.
CLAUDE.md                 When a conflict is ruled on ... record it in the same session: in KNOWLEDGE.md
```

A session in a repo with no orchestrator has nobody to send `FOUND` to, and it is told both to record a ruling and never to write the ruling document.

The why agents traced this to one cause: there is no rule for which file holds which rule. So the same rule stands in two or three files, and each copy drifts. More cases of the same cause:

- CLAUDE.md keeps its own copies of three rules the import already holds: write every change as if it ships to production, stop and ask after two or three failed attempts, and never read secret files.
- No sentence says which file wins when two disagree, so every exception for the orchestrator is written into CLAUDE.md beside the general rule it overrides.
- How to write down a ruling (a Ruled line with the date, who and the reason; the old text in a history file) is written out in five files. CLAUDE.md names the file KNOWLEDGE.md, while LogosLang's ruling document is DESIGN.md.
- The orchestrator skill says twice that a ruling on how the orchestrator works is recorded in the skill, and its other rules about its own files are spread over three sections.

## 1. Where an unsettled decision waits, in every session
**Decision:** whether your own sessions stop putting unsettled decisions in mem0 and auto-memory · **Recommended:** (a) · **Why:** mem0 is not connected, and auto-memory is seen only by sessions started in one folder on this machine

---

Your CLAUDE.md says two things about a decision that is not settled yet:

- Under `## Code Changes`: "Probable decisions can still be stored in mem0 for future reference even before confirmation".
- Under `## Rulings and their records`: a ruling whose wording must wait goes "as an explicit pending edit in auto-memory".

The GoT steps also ask: "Does this conflict with mem0 memories?"

No mem0 server is connected on this machine: `claude mcp list` on 8 October 2026 lists Claude Docs, Gmail, Google Drive, Outline, linear and a few others, and no mem0. So those decisions are stored nowhere. Auto-memory is read only by sessions started in that same folder on this machine; the team, the agents and other orchestrators never see it. That is why you barred the orchestrator from it on 5 October 2026. The orchestrator writes a Pending line instead, at the rule the decision touches, in the repo's ruling document. For example, under a rule in DESIGN.md:

```
- **Pending (<date>, Thobias, <question>):** <your words>; waits for <what must be settled first>.
```

It becomes a Ruled line when the wait ends.

- (a) **A Pending line, in every session.** Every session, with or without an orchestrator, writes an unsettled decision or a waiting wording as a Pending line at the rule it touches, in the repo's ruling document (or in the orchestrator skill, for a rule of the skill). mem0 leaves your CLAUDE.md, and the GoT check becomes "Does this conflict with the ruling document, or a Pending line in it?". Auto-memory keeps what it holds about you and how you like to work; only rulings and waiting decisions stop going there. Nothing already in auto-memory is moved or deleted.
- (b) **Keep mem0 and auto-memory for sessions without an orchestrator.** They stay in CLAUDE.md, with the orchestrator's exception beside them, and those decisions stay stored nowhere until a mem0 server is connected.

Recommended: (a), because a decision kept where no other session reads it, or in a server that does not exist, is a decision lost. It also removes the orchestrator's exception, so one rule holds for every session.
