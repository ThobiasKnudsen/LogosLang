## 1. `free` of an `if` whose two arms are named pointers
**Decision:** what `free (if c (p) else (q))` does · **Recommended:** (a) · **Why:** it says plainly which value ends, as your Q72 answer 2 chose refusing over guessing

---

Your answer 4 lets `free` take an `if` that ends in `else` and whose every arm gives a pointer. Your answer 2 lets an `if` borrow in every arm. Together they allow this:

```logos
p := alloc 1 of i32 5,
q := alloc 1 of i32 6,
mut c := true,
free (if c (p) else (q))
```

Which names are dead after the last line? ›`move` and `free` are static‹ says who owns a value is known before the program runs ("There is no "maybe moved""), but which arm runs is known only when it runs.

- (a) **Refused where it is written:** "free a named value by its name". You write `if c (free p) else (free q)` instead.
- (b) **Both names end there,** as `if c (free p) else (free q)` already ends both today: the arm that runs frees its pointer, and at the `if`'s close the other name is freed at the end of the other arm (rule 2 of ›`move` and `free` are static‹).
- (c) **Only the pointer of the arm that ran is freed.** The other name would be "maybe freed", which the static rule rules out.

Recommended: (a), because a reader of `free (if c (p) else (q))` expects one value to end, and under (b) both end.

## 3. How an imported `pub` name reaches the importer
**Decision:** what the importer's name is · **Recommended:** (a) · **Why:** the seed already does what your proposal is after, without the extra step and without a new rule for writes

---

The answer to your question of how it works today is below, under "Your questions from Q72". In short: the seed already makes a new name in the importer's scope for each `pub` name, and that name reaches the very place the file made, with no copy. Your proposal differs in one point: the new name's type would be `dyad`, pointing at the file's name, instead of the file name's own type. DESIGN's 29 September line says "the importer's name is the same record with the same gates", which can be read as one record shared by both, so it decides nothing here.

```logos
# lib.logos
pub mut counter := i32 10,
pub peek := fn () -> i32 ( return counter ),
```
```
logos 'import ./lib.logos, counter = i32 11, peek()'     # prints 11 today
```

- (a) **As the seed does it.** The importer's `counter` is a name of its own with the file name's type (`i32`) and gates (`pub mut`), over the very same bytes. A read goes straight to the bytes. The 29 September line is reworded to say so.
- (b) **Your proposal.** The importer's `counter` is a `dyad` that points at the file's `counter`. A read takes one step more, through the `dyad`. A write needs a new rule: DESIGN says writing a `dyad` place that holds a node replaces that node and frees the old one, so today's rules would make `counter = i32 11` give the importer's `counter` a new node and free the file's; the file and the other importers would then no longer see the write.
- (c) **One record shared.** No new record: the file's own name is entered in the importer's name index too. A name's record holds one scope and one life, so the lookup rules, which find a name by its record's scope, would need a change for it.

Under (a) and (b), the importer's name and the file's name each have their own end of life, and that is problem P93 below. Under (c) there is one life.

Recommended: (a), because it already gives what you asked for, a new name where the import stands that reaches what the file made, and (b) would need a rule that a write through an imported `dyad` goes into what it points at.

## Your questions from Q72
These are answers to you, so there is nothing to answer here.

**How does Rust solve an `if` that makes a value in one arm and borrows in the other?** It refuses it, as you chose in answer 2. In Rust, whether a value is owned or borrowed is part of its type: an owned list is `Vec<i32>`, a borrowed one is `&Vec<i32>`. Both arms of an `if` must have one type, so this is a type error:

```rust
let a = vec![1, 2];
let x = if c { vec![3, 4, 5] } else { &a };   // error: `if` and `else` have incompatible types
```

When a program really wants either one, Rust's standard library has a type for it, `Cow` ("clone on write"). A `Cow` is either `Owned` or `Borrowed`, with a tag that is read when the program runs, and it frees its value only when it owns it:

```rust
let x: Cow<[i32]> = if c { Cow::Owned(vec![3, 4, 5]) } else { Cow::Borrowed(&a[..]) };
```

That is option (c) of Q72's point 2, the hidden "made or borrowed" flag, but made visible: the programmer writes the type. Logos can have the same as a type written in Logos, with no change to the language. A sketch, not checked against the seed:

```logos
maybe_owned := type ( p := @i32 ?, owns := bool ?, share free = ( if owns (free p) ) )
```

In one place Rust is more lenient than Logos. `if c { drop(a); }` compiles in Rust: Rust keeps a hidden flag on the stack and frees `a` at the end of its scope only if the `if` did not. Logos decided against such a flag (›`free` and `move` end a name; no drop flag‹): the other arm frees `a` at its end, so `a` ends on every path, and nothing is checked while the program runs. So Logos is at least as good as Rust here: the same refusal, the same way out through a type, and no hidden run-time flag.

**How does an importer reach a file's `pub` names today?** A helper read the seed and ran it (commit b101dfd). When `import ./lib.logos` is read, the file is loaded once per run, in its own scope that cannot see the importer's names. It runs top to bottom, and its `pub` names are collected. Then, for each `pub` name, the importer's scope gets a new entry in its name index (the "trie") and a new name record. That record carries the file name's gates, the very same list, and, for a value such as `counter`, the same place in memory: the same frame and offset. For a function or a type, the new record points at the very node the file made. Nothing is copied. A second importer gets its own record over the same place, so a write by one importer is seen by the file and by every other importer. You can see the two records over one place: in a file `self.logos` holding `pub mut v := i32 1, pub v_scope := v:scope, pub v_offset := v:offset,`, the program `import ./self.logos, v:offset == v_offset` prints `true` (same bytes), while `v:scope == v_scope` prints `false` (different records).

Two problems were found on the way, and they are in the problem graph:
- **P92:** a `pub` name declared as a pattern (`pub regex «[0-9]+\\.k» := type ()`) reaches the importer as its literal spelling, not as a pattern, so `(5.k).type == type` works on the command line and fails after an import.
- **P93:** freeing an imported name ends only the importer's own name. With `heap.logos` holding `pub c := alloc 1 of i32 7, pub get := fn () -> i32 ( return c@ ),`, the program `import ./heap.logos, free c, get()` is accepted, and then fails while it runs with "this pointer holds nothing yet".
