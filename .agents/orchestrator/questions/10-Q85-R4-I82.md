## What this is about

`dyad` is the general box: a place that can hold a node of any type. A function declared `-> dyad` gives back such a box. This program crashes:

```logos
f := fn () -> dyad ( i32 5 ), x := f(), print «{x}»
```

- On `dev` it stops with an internal Rust panic, "invalid NumType tag 24", exit 1.
- On the branch of issue 82 (the work that teaches every node what type it gives, which is about to merge), it is a memory fault (segmentation fault), exit 139.

Why: the issue 82 branch made calls of `-> dyad` functions run, where `dev` refused them by accident. The call gives back the bare number 5, but every reader after it treats what a `dyad` place holds as the address of a node, so it reads memory at address 5. `x` alone, `x.type`, `y := x` and `f := fn (a) -> dyad ( a ), x := f(i32 5), print «{x}»` crash the same way.

What already works on the branch: `print «{f()}»` prints `5`, and `f := fn () -> dyad ( i32 ), x := f(), print «{x}»` prints `i32`.

DESIGN already says what should happen, in ›A `dyad ?` place is transparent: a placeholder for a new node of any type‹: "`mut d := dyad ?, d = i64 5` fills `d` with a new `i64` node." The seed has not built that yet. Today `=` refuses a number into a `dyad ?` place, and the rule's Seed line says so: "not yet: a `dyad ?` place takes only a type-valued write". So, by DESIGN, `f()` should give back a new `i32` node holding 5, and `print «{x}»` should print `5`.

## 1. What the issue 82 branch does before it merges
**Decision:** refuse a number as a `-> dyad` result for now, or build the new-node behaviour now · **Recommended:** (a) · **Why:** the smallest change that ends the crash, the same refusal `=` already makes, and the real behaviour comes with the one conversion path you are deciding in Q83

---

- (a) **Refuse it for now, as `=` does.** A `-> dyad` function may give back only what `=` lets into a `dyad ?` place today: a type such as `i32`, not a number. `f := fn () -> dyad ( i32 5 )` becomes an error where `f` is defined. To close every crash, giving back a parameter from a `-> dyad` function is refused too, since a parameter may hold a number: `f := fn (a) -> dyad ( a )` becomes an error. That also refuses `f := fn (d := dyad ?) -> dyad ( d ), f(i32)`, which works on the branch now. The fix for one conversion path for every spot (Q83, the question beside this one) then removes this refusal and builds the new-node behaviour for every spot at once.
- (b) **Build the new-node behaviour now, on the issue 82 branch.** A number going into a `dyad ?` place becomes a new node of its type, for `=`, for a parameter and for a `-> dyad` result. The first program prints `5`. This is new work, not a review fix, so issue 82 merges later, and it builds one of the spots Q83's answer decides before that answer.

Merging the branch as it is would turn `dev`'s panic into a memory fault, so the reviewer recommends against it.

Recommended: (a), because it ends the crash with the smallest change, it refuses exactly what `=` refuses today, and the behaviour DESIGN rules comes once, for every spot, with Q83's one conversion path.
