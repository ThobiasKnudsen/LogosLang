## What this is about

`dyad` is the general box: a place that can hold a node of any type. A function declared `-> dyad` gives back such a box. This program crashes:

```logos
f := fn () -> dyad ( i32 5 ), x := f(), print «{x}»
```

- On `dev` it stops with an internal Rust panic, "invalid NumType tag 24", exit 1.
- On the branch of issue 82 (the work that teaches every node what type it gives, which is about to merge), it is a memory fault (segmentation fault), exit 139.

Why: the issue 82 branch made calls of `-> dyad` functions run, where `dev` refused them by accident. The call gives back the bare number 5, but every reader after it treats what a `dyad` place holds as the address of a node, so it reads memory at address 5. `x` alone, `x.type`, `y := x` and `f := fn (a) -> dyad ( a ), x := f(i32 5), print «{x}»` crash the same way.

What already works on the branch: `print «{f()}»` prints `5`, and `f := fn () -> dyad ( i32 ), x := f(), print «{x}»` prints `i32`.

DESIGN already says what should happen, in ›A `dyad ?` place is transparent: a placeholder for a new node of any type‹: "`mut d := dyad ?, d = i64 5` fills `d` with a new `i64` node." The seed has not built that yet. Today `=` refuses a number into a `dyad ?` place, and the rule's Seed line says so: "not yet: a `dyad ?` place takes only a type-valued write". So, by DESIGN, `f()` should give back a new `i32` node holding 5, and `print «{x}»` should print `5`.

## 1. What the issue 82 branch does before it merges
**Decision:** refuse a number as a `-> dyad` result for now, or build the new-node behaviour now · **Recommended:** (a) · **Why:** the smallest change that ends the crash, the same refusal `=` already makes, and the real behaviour comes with the one conversion path you are deciding in Q83

---

- (a) **Refuse it for now, as `=` does.** A `-> dyad` function may give back only what `=` lets into a `dyad ?` place today: a type such as `i32`, not a number. `f := fn () -> dyad ( i32 5 )` becomes an error where `f` is defined. To close every crash, giving back a parameter from a `-> dyad` function is refused too, since a parameter may hold a number: `f := fn (a) -> dyad ( a )` becomes an error. That also refuses `f := fn (d := dyad ?) -> dyad ( d ), f(i32)`, which works on the branch now. The fix for one conversion path for every spot (Q83, the question beside this one) then removes this refusal and builds the new-node behaviour for every spot at once.
- (b) **Build the new-node behaviour now, on the issue 82 branch.** A number going into a `dyad ?` place becomes a new node of its type, for `=`, for a parameter and for a `-> dyad` result. The first program prints `5`. This is new work, not a review fix, so issue 82 merges later, and it builds one of the spots Q83's answer decides before that answer.

Merging the branch as it is would turn `dev`'s panic into a memory fault, so the reviewer recommends against it.

Recommended: (a), because it ends the crash with the smallest change, it refuses exactly what `=` refuses today, and the behaviour DESIGN rules comes once, for every spot, with Q83's one conversion path.

## 2. Merge issue 82 with a known slowdown and a few wrong answers about who owns a function's result, or fix their cause first?
**Decision:** whether the issue 82 branch merges once question 1 is built, or waits until the cause below is fixed on it · **Recommended:** (a) · **Why:** the fix of the cause needs a ruling of yours first, and holding issue 82 holds every fix that waits for it

---

Review round 5 found the branch clean, apart from question 1. But reviews 4 and 5 found that the branch does some things worse than `dev` does, all from one cause. To follow your 8 October ruling (Q72: an `if` that gives a value either makes it in every arm or borrows it in every arm), the parser works out whether a function makes its result or borrows it by walking the function's body, and the bodies of the functions it calls, each time it is asked. It never keeps the answer. Three separate walks over the same `if`s and blocks answer the type, the owner and the ending.

What that does on the branch:

- **Reading gets very slow for one shape of program.** 22 functions, each calling the one before it in both arms of an `if`, take 1 second to read on the branch and 0.01 seconds on `dev`, and the time doubles with each extra function, so about 30 would take minutes. Nothing runs; the program is only read. A 2,000-arm `else if` chain takes time that grows with the square of its length.
- **A program `dev` runs is refused.**
  ```logos
  mk := fn (n := i32 ?) -> @i32 ( if (n == 0) (alloc 1 of i32 5) else ( x := mk(n - 1), x ) ), y := mk(3), print «{y@}»
  ```
  The branch says "make a value in every arm, or borrow in every arm", though both arms make one. The walk stops at a function calling itself, so a name bound to such a call looks like a borrow. (`dev` runs it, and leaks the value.)
- **Some mixed `if`s are let through, and leak.** With `mk` as above, `x := if (c == 1) (mk(3)) else (&y)` is accepted, though Q72 refuses it. The walk also gives up after 32 levels of calls.

Nothing is freed twice and nothing crashes from this cause. The reviewer's fix for it: work out once, at a function's end, whether it makes or borrows its result, and keep that with the function, as Rust puts it in a function's signature. That is a ruling of yours: your Q72 ruling says an `if` and a block keep no record of what they give, and a function's result would then keep one.

- (a) **Merge once question 1 is built.** The slowdown, the refusal and the leaks go into the problem graph as one cause, and its fix comes to you as its own question. `dev` meanwhile gets everything issue 82 fixes, and the fixes waiting for it can start.
- (b) **Hold the merge until the cause is fixed on this branch.** `dev` never has the slowdown or the refusal. Issue 82 waits for that question, its answer and the work, and so does everything that waits for issue 82.

Recommended: (a), because the fix needs your ruling on where a function keeps who owns its result, the slow shape needs a long chain of functions calling each other in both arms, and holding issue 82 holds many other fixes.
