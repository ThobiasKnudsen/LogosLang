At ›A type's `parse` decides what converts into it; unwritten, a value converts only into a type that holds it exactly‹, the paragraph "Where a value meets a type it is not and no conversion is written…" becomes:

> Where a value meets a type it is not, it converts when that type's `parse` takes it and the value's type lies inside that type, whether the conversion is written (`i64 m`) or not (`x = m`, an argument, a result, an operand, an `if`'s arm). The value's type decides, never the one value: with `mut x := f64 0.0`, `x = f32 9` writes `9.0`; `i32 1 + i64 2` is `i64` addition; `x = if c (1) else (f64 2.5)` writes an `f64` either way. An integer type lies inside a float type only when the float holds every value of it: `i32` inside `f64`, not `f32`; `i64` not inside `f64`. `⊆` answers the same: `i32 ⊆ f64` is `true`. Otherwise the value is refused where it is written, even when the one value fits: `a = i64 4` into an `i32`, `i32 (i64 4)` and `i32 (f64 2.5)` are refused. **[2]** A conversion that may lose is written `lossy` in front of the type: `lossy i32 (f64 2.5)` is `2`, `lossy i32 (i64 5000000000)` wraps to `705032704`, `lossy f32 (i32 16777217)` is `16777216.0`. An unwritten conversion is in the graph as the node the written one makes, and nothing is where the types match.
