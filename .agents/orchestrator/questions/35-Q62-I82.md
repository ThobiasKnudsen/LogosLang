## 1. Do we need `match` at all?

**Your reply (9 October 2026):** "why not just NOT have match at all? i dont see why not if else can be used instead. what exactly is a pattern for each match arm? and what do you mean by that the arm can name what it finds?"

**Where `match` comes from.** DESIGN has `match` in one place only, the error rule ›Target: errors are values (`T!`), handled by `match`, passed on by `try`‹ (30 and 31 August 2026). A function that can fail returns `T!`: either a `T` or an error. That rule says the caller handles such a result with `match`. DESIGN has no spelling for `match` yet, so the examples below use a made-up one.

**What a pattern is.** A pattern is a test on the shape of a value that also takes a piece out of it. A `T!` value has two shapes, "an `i32`" or "an error", so a `match` on it has two arms:

```
r := read_number(«42»),                        # r is i32!: an i32 or an error
match r (
  i32 n   (print «got {n}»),                   # pattern 1: r holds an i32; call it n
  error e (print «failed: {e[0].message}»)     # pattern 2: r holds an error; call it e
)
```

**What "name what it finds" means.** In the first arm, `n` is a new name for the `i32` inside `r`, and it exists only in that arm. In the second arm, `e` is the error inside `r`. So you cannot write `n` in the error arm by mistake: there is no `n` there.

**The same with `if`.** It works if a `T!` value has three fields of its own. The names here are only placeholders, chosen when error values are built:

```
r := read_number(«42»),
if r.is_error (print «failed: {r.error[0].message}») else (print «got {r.value}»)
```

What `if` loses: nothing stops you from writing `r.value` in the error arm. That mistake is found only when the line runs, as an error then; with `match` it cannot be written. Everything else is the same. And `try`, which the error rule calls "sugar over `match`", becomes sugar over `if`: `try f()` means "if the result is an error, return it from this function; else give its value".

- (a) **No `match`.** The error rule becomes "handled by `if`, passed on by `try`". A `T!` value has fields for "is it an error", "the value" and "the error"; reading the value of an error, or the error of a value, is an error when the line runs. A library may still define a `match` later, as its own type with its own `parse` (›A type's `parse` is unrestricted code‹), so the core needs no word for it.
- (b) **Keep `match` for later.** The error rule keeps "handled by `match`", and its form is decided when error values are built.

Recommended: (a). It deletes a word from the core, `if` already does the job, and the one thing `match` adds can still come from a library.
