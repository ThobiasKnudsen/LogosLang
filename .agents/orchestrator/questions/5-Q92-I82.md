## 1. Where does `own` go for a type's `run`?
**Decision:** how a type's `run` hands on a value it made · **Recommended:** (a) · **Why:** `array` keeps working and stays fast

---

Your Q89 choice says a function hands on a value it made only when its result type says `own`:

```
mk := fn () -> own @i32 ( alloc 1 of i32 5 )
```

Issue 82 (the branch that works out what type each node gives) is building that now. But a type's `run` is a function with no `->`, so it has no place to write `own`. And the `array` type's `run` makes a new array and hands it on, as DESIGN says it must. So, built as written, this stops working on the branch:

```
import ./identities/array.logos, x := array i32 [1, 2], x[1]
```

It stops with: "this type's `run` hands on a value it made, and a `run` has no `->` to write `own` in".

The two rules that meet here:
- ›Three fail-closed ownership rules, and `-> own @T`‹: "rule 3 has one door: `-> own @T`, or `-> own t` for a type that fills `free`".
- ›An array expression is a node of `array`, and its run makes the value‹: "The node's `run` allocates a value of the mint, assigns each line with `=` and returns it."

- (a) **The `run` marks itself.** When a type's `run` body is read, the reader works out once whether its last value is made. If it is, the reader writes `own` on that `run` itself, as if you had written `-> own`. A call then reads only that mark and never the body, so it stays fast. `array` works as before. In a `fn`, you still write `own` yourself.
- (b) **A `run` must say it too.** You choose a way to write `own` on a `run`. Until then, `array i32 [1, 2]` gives the error above, and issue 82 cannot merge.

Recommended: (a), because `array` keeps working and calls stay fast, and a written spelling for a `run` can still come later and replace the mark.
