## The cause, in plain words

›A call is a use of every outer name the callee's body reads‹ refuses a call when a name the function reads from outside has ended (freed, moved, or out of scope), and that counts names read by functions it calls too.

The seed copies each callee's whole list of outside names into the caller's list. In a chain where `h1` calls `h0`, `h2` calls `h1`, and so on, `h2000`'s list holds `h0` up to `h1999`, and every call checks that whole list again. Nothing is kept between calls, and DESIGN.md does not say what may be kept.

Your rule of 9 October, ›Reading a program takes time in step with its size; no walk runs once per path‹, says: "An answer a walk needs again for the same node is kept." A kept answer must still catch a name that ends between two calls:

```
x := alloc 1 of i32 5, h0 := fn () -> i32 ( x@ ), h1 := fn () -> i32 ( h0() ), print «{h1()}», free x, h1()
```

Today the first `h1()` passes and the second is refused ("`x` is dead here"). That must stay.

**Proof:** `c := i32 1, h0 := fn () -> i32 ( i32 5 ), h1 := fn () -> i32 ( if (c == 1) (h0()) else (h0()) ), …, 7`, nothing ever called, prints `7` after 75 ms at 500 functions, 382 ms at 1,000, 1,730 ms at 2,000 (dev 209fd88). That is about five times slower per doubling, where the rule asks for about twice.

## 1. What may a function keep, and what makes it check again?
**Decision:** when a function's kept check answer goes stale · **Recommended:** (a) · **Why:** the chain reads in step with its length, and your 8 September decline stays as it is

---

Both options stop copying lists: a function's list holds only the names its own body reads and the functions it calls, and a call asks each of those functions for its own answer. The refusal above stays. This also helps Q87, your open question on bodies built later.

- (a) **Kept until any name ends.** Each function keeps its last answer. The parse counts how many names read by some function have ended, and a function checks again only when that count has grown. Cost: one number per function. Worst case: a program that ends a name between each call of a long chain checks the chain again each time.
- (b) **Kept until a name it reads ends.** Each name that can end keeps a list of the functions that read it, and its end marks them and their callers refused. Always in step with the program's size. But this is the "per-binding list of the declarations using a name" you declined on 8 September at ›The reader–writer rule is transitive, and resolution is a read‹ ("Rejected, to stay declined"), so (b) reverses that.

The words (a) would add under ›A call is a use of every outer name the callee's body reads‹:

> - **Ruled (<date>, Thobias):** a function's list holds the outside names its own body reads and the functions its body calls, not theirs. A call checks its callee's names and asks each function on the list for its own answer. A function keeps the answer of its last check, and checks again only after a name some function body reads has ended (`free`, `move` or its scope's close). **Why:** <your words>.

Its Why sentence "The check is a range lookup per outer name per call" moves to DESIGN_HISTORY.md. (b)'s words are the same, with "kept until a name it reads, or a body it calls reads, ends", and its Rejected line changes.
