## 1. May the bottleneck order start an implementation agent without you naming the issue?
**Decision:** which issues the orchestrator may start by itself · **Recommended:** (c) · **Why:** a chosen solution already holds your choice, and any other issue still waits for your word.

---

Your rule from Q77 says the orchestrator starts next whatever holds the project back the most, and you listed implementation agents among the work it starts. An implementation agent is the agent that builds one issue on its own branch. The skill also has an older rule from before: "Never start an issue he did not name." The two rules disagree, so I wrote your rule with a Pending line, and until you answer, an issue starts only when you name it.

In this repo the question is real today: three solutions are chosen. S1 (every built-in's parse writes the type its node gives back) is issue 82, which is being reviewed. S4 (a value's life ends where its type's `free` slot runs) is issue 192, which is merged. S19 (a local name may not be declared as an empty owning hole) is issue 241, which nobody has started yet: under (a) or (c) it would start when the bottleneck order reaches it.

- (a) **Any open issue.** The orchestrator starts an implementation agent on any open issue the bottleneck finder ranks highest, and tells you in one line which one it started. You can stop it at any time.
- (b) **Only issues you name.** The bottleneck order decides only when why agents, solution agents and reviews run. The bottleneck finder's list tells you which issue to name next.
- (c) **Issues made from a solution you chose, and issues you name.** An issue that a solution agent wrote from a solution you chose starts when the bottleneck order reaches it, since choosing the solution was your choice to build it. Any other issue, such as one written before the problem graph existed, still starts only when you name it.

Recommended: (c), because only a solution you chose becomes an issue, so starting it needs no second yes from you, while an older issue may never have been chosen by you at all.

## Your questions from Q77

**Why not BM25?** You were right, and I measured it. BM25 is a refinement of TF-IDF: a rare word counts more, and a word repeated many times in one long text counts less. I had picked TF-IDF because BM25 is made for ranking documents against a search query, but its word weights can be compared between two texts in the same way. I tested both on the 116 pairs of nodes that were merged so far, in LogosLang, AI-RCA and the website. Each such pair is one fact that two agents wrote in different words, so a good measure should score them high.
- Today's word count found 52% of those pairs at 0.3, the score from which `compare` treats two drafts as the same fact, and 83% at 0.2, the score from which `similar` shows a node.
- BM25 found 92% at 0.3 and 98% at 0.2.
- It also showed fewer unrelated pairs for the same number found: at 0.3 it found 92% and showed 335 other pairs; today's count at 0.2 found only 83% and showed 439.

So `pws.py` now uses BM25, with simple stemming, so that "freed" and "frees" count as one word. `similar` shows a node from 0.25 on (97% of the merged pairs) and `compare` groups from 0.3. An example: the search "cells freed twice by readers" now finds the cause "the reader frees the cell twice". Before, only the word "twice" matched, a score of 0.14, below the line. The tests for `pws.py` all pass (29, two of them new).

**Will it become slow at 1,000, 10,000, 100,000 or 1 million nodes?** I timed it on copies of AI-RCA's graph made larger. Each `pws.py` command reads the whole `PWS.json`, and each write writes the whole file again.

| Nodes | File | One search | One write |
| :- | :- | :- | :- |
| 1,485 | 4.6 MB | 0.3 seconds | 0.2 seconds |
| 10,395 | 32 MB | 2.3 seconds | 1.6 seconds |
| 100,485 | 311 MB | about 25 seconds | about 17 seconds |

So it is fine up to about 10,000 nodes. At 100,000 it is too slow for the why agents, who run many commands, and the file is over GitHub's limit of 100 MB per file (GitHub warns from 50 MB). At 1 million it would take minutes per command and the file would be about 3 GB. The graphs grow fast: AI-RCA's has 495 nodes after 6 days, about 83 a day, so it reaches 10,000 nodes in about 4 months and the 50 MB warning in about 6 months. LogosLang's has 208 nodes after 8 days. I recorded this as problem P85, so it is taken in the bottleneck order like any other problem.

**PostgreSQL, another database, or files on GitHub?** My recommendation for P85's solution agent, before about 10,000 nodes: keep every node as its own small file in the repo, for example `.agents/orchestrator/pws/W269.json`, so all of them stay on GitHub, and a write changes one small file. Beside them, a search index in SQLite, a database that is a single file and needs no server. The index is not committed; it is rebuilt from the node files in a few seconds whenever they change. SQLite has full-text search with BM25 built in, the same measure `pws.py` uses now, so the scores stay the same and a search over a million nodes takes milliseconds. PostgreSQL is a server that must run somewhere and be shared between machines, and the nodes would no longer be files in git; it gives nothing this needs.
