## 1. Which solution for W75?

**The root cause, in plain words.** A scope's lines are run by one Rust function, `run` in `src/identities/scope.rs`. It does two jobs in one go: it runs the lines from a start to the last one, and then it ends the scope (`run_exit`, or `run_exit_after_fault` when a line faults). There is no step that says "run the lines up to here and keep the scope open".

The pass needs exactly that step. ›The pass runs only as far as it must, in order, and never twice‹ says: when the parse needs a value, "everything parsed before that point and not yet run runs first, in order", and "A frame keeps a cursor, how far the scope it runs has got". Since `run` would also end the scope, the pass cannot call it, so it keeps a second runner of the same lines in `src/parse/bodies.rs`:

- its own loop over lines not yet run (`drain` over `OpenScope.unrun`);
- its own position (`OpenScope.ran`), handed to `run` as a note on the frame (`set_cursor`), which `run` reads and deletes (`take_cursor`);
- since #192 merged, its own record of which names a run line ended (`OpenScope.reached`) and its own fault exit (`end_after_fault`), beside `run`'s loop index and `run_exit_after_fault`.

So #192 made the duplicate bigger: two runners, two positions, and now two ways to end a scope after a fault.

A Logos example where both runners touch one block:

```
( n := i32 2, v := immediate ( n + 1 ), defer print «bye», print v )
```

`immediate` needs `n` while parsing, so `drain` runs line 0 with its own loop and writes cursor 1. Later the block runs as a whole: `run` takes the cursor, skips line 0, runs the rest, then prints `bye`. If line 0 had faulted, the pass's `end_after_fault` would end the block; if line 3 faults, `run`'s `run_exit_after_fault` does.

**What it explains.** One open problem, P29, through a long chain: W75 (two jobs in one function) → W73 (the pass runs lines itself) → W71 (three runners of a scope's lines, each with its own position and exit) → W68 (the frame does not keep the cursor while the scope runs) → W64/W63 (what a live scope owes sits in Rust, not in data) → W62/W60/W59/W58 (compiled code has no way out at a fault) → P29. Rerun on dev ac86218, it still fails:

```
p := alloc 1 of i32 5
g := fn () -> i32 ( error «stop» )
f := fn () -> i32 ( g(), p@ = 9, 1 )
f.compile()
f()
p@
```

```
» » » » » run error: stop
» 9
```

It should print `5`, as it does interpreted. To be honest about it: fixing W75 alone does **not** fix P29. P29 lives at the bottom of the chain, in the compiled tier (W58 to W60). W75 is the top of that chain: the pass's second runner.

**Related root causes.**
- W12 (five readers of a scope's lines, each with its own end rule; solution S9, #234): the same heading. The top level has a scope node now (#192 hands it the program's exit), but its lines are not stored in it, only counted (`OpenScope.lines`); S9's one reader would put them there, which S20 needs.
- W4 (every identity written twice, once per tier; solution S3, #164): owns the third runner, `lower_with_teardowns` in `compile.rs`, and so most of P29.
- W9 (a body built later is parsed again by one of two builders): rests on the same heading, no shared code.

**The options.**

- (a) **S20: two steps on the scope identity.** `advance(scope, upto)` runs the lines from the frame's cursor up to a line, moves the cursor, and leaves the scope open. `run_exit` ends it. A scope's own run is just "advance to the last line, then exit"; a fault in any line, run by the pass or by the scope, ends the scope through the one `run_exit_after_fault` at the cursor. `drain` calls `advance` for each open scope, so its loop, `unrun`, `ran`, `reached`, `end_after_fault` and the `set_cursor`/`take_cursor` hand-off are deleted (whether `reached` goes whole is checked in the slice: `run_exit_after_fault` reads a NULL place where the pass keeps a list). The cursor stays on the frame the whole run, as the rule says. Root fix: one runner in the interpreter, one cursor, one fault end. Leaves the compiled tier as it is (P29 stays). Waits for #234 (S9), so the top level's lines live in its scope node. About 200 lines in `scope.rs`, `bodies.rs`, `run.rs`. No DESIGN change: the rule already says this.
- (b) **S21: a mode flag.** `run(scope, upto, exit: bool)`: `drain` calls it with exit off. Smallest change, and it does not wait for #234, but it fixes only the symptom: one function with two modes, and the pass still keeps its own position, its own `reached` and its own fault end. I recommend against it.
- (c) **S22: S20 plus a stack of live scopes on the frame.** As (a), and the frame also keeps each live scope (node and cursor) as data, so a `return`, a fault or a cancel ends every live scope from that stack instead of from a Rust error passing back through each `run`. Also removes W68 and the interpreter half of W63/W64, which ›Scheduling, preemption, and cancellation happen at boundaries‹ ("running its live scopes' pending `defer`s") will need. Twice the size of (a), and that rule is "Seed: not yet", in the adaptive layer after v1.0.0. Better as a later step on top of (a).

Recommended: (a), because it removes the root (one runner, one cursor, one fault end) with the smallest change that does so, and it is what the rule already says. (c) can follow later on top of it.

If you choose (a), no DESIGN wording changes; the issue would start `Solution S20 for W75 (chosen <date>)` and `Blocked by #234`.
