## What this is about

In Logos a value often goes into a spot that already has a type. It happens in many ways:

```
mut a := i32 5, a = i64 4                      # into the name a, which is an i32
g := fn (x := i32 ?) -> i32 ( x ), g(i64 4)    # into the parameter x, which is an i32
f := fn () -> i32 ( i64 4 )                    # the function's result, which is an i32
```

In the seed each of these ways has its own separate check, written in Rust. There are eight of them, and they do not agree. The function result's check is missing a part, so this prints a wrong number instead of an error:

```
f := fn () -> i32 ( f64 2.5 ), f()             # prints 0 today
```

You agreed that `f := fn () -> @i32 ( i32 5 ), p := f(), p@` must be an error, because a pointer must be given back, not a number. Every option below makes it one. You also agreed that `true` never goes into a number and a number never goes into a `bool`. That is now recorded in DESIGN.md.

Your comment said the fix is one conversion path for all of these, the same one `=` uses. I agree, and that is the fix. But three things in your comment need your choice first.

## 1. Your example `a = i64 4` against your 2 October rule
**Decision:** whether a typed value converts by its type or by its value · **Recommended:** (a) · **Why:** one answer when the program is read, the same for `i64 4`, a name holding it, and a function's result

---

You wrote: "`a := i32 5, a = i64 4 # a is now i32 4`, since i assume this works now". It does not work today:

```
mut a := i32 5, a = i64 4, a        # error: these types do not match
mut a := i32 5, a = 4, a            # 4      (a plain number converts when its value fits)
mut a := i32 5, a = i32 (i64 4), a  # 4      (the conversion written)
```

Your rule of 2 October says the same as the seed. Its heading is ›A type's `parse` decides what converts into it; unwritten, a value converts only into a type that holds it exactly‹, and it says a value converts without its type written only when the value's TYPE fits inside the type it goes into. Every `i32` fits in an `i64`, but not every `i64` fits in an `i32`. So by your rule `a = i64 4` is refused, even though the number 4 fits. Your example asks for something else: convert when the VALUE fits.

The difference shows when the value is not known until the program runs:

```
mut a := i32 5, a = i64 4                                  # value known while reading
b := i64 4, mut a := i32 5, a = b                          # value known while reading, through a name
g := fn () -> i64 ( i64 4 ), mut a := i32 5, a = g()       # value known only when g runs
```

- (a) **By type, as your 2 October rule says.** All three lines are errors where they are written. You write `a = i32 (i64 4)`, or `a = 4`. A plain number like `4` still converts when its value fits, as today.
- (b) **By value when it is known while reading, by type otherwise.** Lines one and two work, and line three is an error. So the same `i64` value behaves differently depending on where it came from.
- (c) **By value always.** All three are accepted while reading. Line three is checked when it runs, and stops the program with an error if `g` gives a number too big for an `i32`.

Recommended: (a), because the reader of the program gets the same answer for every line, and nothing can fail later at run.

## 2. Is "fits exactly" too strict for integers into floats?
**Decision:** what happens, without a conversion written, when an integer goes where a float is needed · **Recommended:** (a) · **Why:** the conversions that never lose stay invisible; the ones that can round are written, as in Rust

---

You asked whether Rust is just as strict. It is stricter. Rust converts no number without it being written, not even `i32` into `i64`. It has two written forms:
- `into()`, which only exists where nothing can be lost. Its table is exactly the "fits inside" test: `i32` into `f64` yes, `i32` into `f32` no, `i64` into `f64` no, `u32` into `i64` yes, `i32` into `u64` no.
- `as`, which always works and may lose: it rounds, cuts or wraps.

So the decided point you questioned is Rust's `into()` table, made automatic. Your "word for approximate cast" is Rust's `as`.

In Logos today, the written conversion already behaves like Rust's `as`:

```
f32 (i32 16777217)       # 16777216.0   (rounded: an f32 holds integers exactly only up to 16777216)
i32 (i64 5000000000)     # 705032704    (wrapped, as + wraps on integers)
i32 (f64 2.5)            # 2            (the fraction is cut)
```

And as you say, `rational_number` computes exactly but slowly, while `i32`, `f64` and the other machine types are fast but may round. `f64 (1/3 + 1/6)` gives `0.5` because the sum is exact before it becomes an `f64` (inside a function; at the top of a program this line hits a known bug today).

- (a) **Strict without writing, and the written conversion is the approximate cast.** `i32` goes into `f64` by itself, `i32` into `f32` needs `f32 x` written, and that written form may round, as it does today. No new word. This also settles a question your rule left open, whether a written conversion is checked like an unwritten one: it is not, it converts as its type defines, rounding included.
- (b) **Strict without writing, the written conversion strict too, and a new word for an approximate cast.** `f32 (i32 16777217)` becomes an error, and a new word, to be chosen later, rounds.
- (c) **Looser without writing.** Every integer goes into every float by itself, rounding where it must: `i64` into `f64` and `i32` into `f32` work without writing.

Recommended: (a), because an unwritten conversion never changes a number, and a rounding one is always visible in the code, which is what Rust does with no new word.

## 3. `=` nodes in the graph
**Decision:** what the graph holds where the code leaves a conversion unwritten · **Recommended:** (a) · **Why:** the graph shows every conversion as if it were written, without a node where nothing happens

---

Your idea, as I understand it: every spot a value goes into with a type (a parameter, a function's result, a record's field, a write through a pointer) runs the same conversion path as `=`. The code does not show an `=` there, but the graph does, as a node. You said it is an idea, not a ruling.

One thing to know: today `=` is not the one path. It is one of the eight separate checks, and it refuses `a = i64 4` as shown above. So the fix builds that one path, and `=` uses it too, like every other spot.

- (a) **A node only where a conversion happens.** Where the types already match, the graph is as today. Where a value converts, the graph gets the same node that writing the conversion gives: `g(i32 7)` into an `i64` parameter is in the graph exactly as `g(i64 (i32 7))` would be. That node is the part of `=` that converts.
- (b) **An `=` node at every spot**, even where nothing converts. Every argument of every call, every function result and every field gets one more node. It is made once, when the program is read, never each time it runs, but the graph grows by one node per argument, and a call's argument is already, in the graph, the filling of its parameter.

Recommended: (a), because it gives what you asked, one path and every conversion visible in the graph, without a node that does nothing.
