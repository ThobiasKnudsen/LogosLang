## What goes wrong

Every `( … )` is a scope whose value is its last line (›A scope's value is what it evaluates to…‹: "Every `( )` is a scope that produces a value"). So `g((i32 4, i32 5))` gives `g` one argument, `5`. The seed gets this wrong on both tiers:

```
g := fn (b := i32 ?) -> i32 ( b ), g((i32 4, i32 5))      run error: a call's argument count does not match its function   (should be 5)
x := i32 ((i32 4, i32 5)), x                              error: a conversion takes exactly one numeric value               (should be 5)
x := dyad ((i32, 5)), x                                   5    (should be an error: one argument, not two)
first ((i32 1, i32 2))                                    1    (should be 2; a silent wrong answer)
```

(`first` is a test type in `tests/fixtures/scope_cell_lines.logos` whose parse takes the first line of the bracket to its right.)

**Why:** when a bracket holds one line, the seed throws the bracket away and keeps the line. DESIGN lists this as a known stand-in (›The seed's tape shape (#60, #121) and its remaining stand-ins‹: "A one-expression bracket is unwrapped to its expression"). So in `g((i32 4, i32 5))` the call's own bracket vanishes, and the inner bracket looks exactly like `g(i32 4, i32 5)`.

## 1. Which fix?
**Decision:** how far the fix goes now · **Recommended:** (a) · **Why:** it fixes every wrong answer found, costs no speed, and is small

---

- (a) **The bracket keeps its scope on its cell.** Everything that reads a bracket as a bracket (a call, a conversion like `i32 (…)`, `dyad (T, v)`, a member call, `tape[k]` in a Logos parse) reads that scope's lines. The built-in operators still read the one line, so `(x + 2) * 3` runs exactly as today. All the programs above give the right answer. No speed cost: the seed already makes that scope and then drops it. About 60 lines. What stays: inside built-in operators `(x + 2)` still stands as `x + 2`, which shows only when a program walks its own graph.
- (b) **Remove the shortcut entirely.** `(` always leaves a scope, for every reader, as DESIGN says, and the stand-in leaves DESIGN. Every built-in operator, the early folding of `(2 + 3) * 4`, and both tiers must then read through a one-line scope. Large, not measured, and may cost a little run time. It can still come later, since (a) already keeps the scope.
- (c) **Keep a bracket only around another bracket.** One condition. Fixes all but `first (i32 7)` (refused, should be `7`), and the count still depends on the kind of node: a patch of the symptom.

## Decided (orchestrator)
Answer "ok" to accept, or write what you want instead.
- `tape[k]` of a one-line bracket gives the bracket's scope, not its line, since ›A bracket goes to the call whole‹ says "the cell a `(` lands is a `scope`". So `first (i32 7)` gives `7`, and a Logos operator with a bracket on its right (like `^` in `identities/power.logos`) holds a scope there; a scope already has its last line's type.
- Under (a), the stand-in line in DESIGN becomes: "A one-expression bracket stands as its expression for the seed's own readers of a value; the cell keeps the scope the `(` landed, and every reader of the bracket reads that scope's lines: a call, a conversion, `dyad (T, v)`, a member call, and `tape[k]` in a parse." No rule changes: ›A bracket goes to the call whole‹ already says "lines are operands".
