## 1. Which solution for W75?

**The root cause, in plain words.** A scope's lines are run by one Rust function, `run` in `src/identities/scope.rs`. It does two jobs in one go: it runs the lines from a start to the last one, and then it ends the scope (runs its `defer`s). There is no step that says "run the lines up to here and keep the scope open".

The pass needs exactly that step. ›The pass runs only as far as it must, in order, and never twice‹ says: when the parse needs a value, "everything parsed before that point and not yet run runs first, in order", and "A frame keeps a cursor, how far the scope it runs has got". Since `run` would also end the scope, the pass cannot call it. So `drain` in `src/parse/bodies.rs` keeps its own list of lines not yet run (`OpenScope.unrun`), runs them with its own loop, and then leaves a note on the frame (`set_cursor`) that `run` picks up and deletes (`take_cursor`) when the scope's own run starts.

A Logos example where both loops touch one scope:

```
( n := i32 2, v := immediate ( n + 1 ), defer print «bye», print v )
```

`immediate` needs `n` while parsing, so `drain` runs line 0 with its own loop and writes cursor 1. Later the scope runs as a whole: `run` takes the cursor, skips line 0, runs the rest, then prints `bye`. Two loops, two ideas of "which line are we on", two places that decide that a `defer` or a comment is skipped.

**What it explains.** One open problem, P29, through a long chain: W75 (two jobs in one function) → W73 (the pass loops itself) → W71 (three runners of a scope's lines, each with its own position and its own exit) → W68 (the frame does not keep the cursor while the scope runs) → W64/W63 (what a live scope still owes sits in a Rust local, not in data) → W62/W60/W59/W58 (compiled code has no way out at a fault) → P29:

```
p := alloc 1 of i32 5
g := fn () -> i32 ( error «stop» )
f := fn () -> i32 ( g(), p@ = 9, 1 )
f.compile()
f()
p@
```

Compiled it prints `run error: stop` and then `9`; interpreted, `p@` is `5`, as it should be. To be honest about it: fixing W75 alone does **not** fix P29. P29 lives at the bottom of the chain, in the compiled tier (W58 to W60). W75 removes the top of the chain: the pass's own runner.

**Related root causes.**

- W4 (every identity written twice, once per tier; solution S3, #164): owns the third runner, `lower_with_teardowns` in `compile.rs`, and so most of P29.

**Already in flight.** #192 (branch `issue-192-teardown-at-life-end`) already pulls the exit out of `run` as its own function, `run_exit(scope, line_reached)`. So half of the split is written; every solution below builds on it and waits for #192.

**The options.**

- (a) **S20: two steps on the scope identity.** `advance(scope, upto)` runs the lines from the frame's cursor up to a line, moves the cursor, and leaves the scope open. `run_exit` (from #192) ends it. A scope's own run is just "advance to the last line, then exit". `drain` calls `advance` for each open scope, so its loop, `OpenScope.unrun` and the `set_cursor`/`take_cursor` hand-off are deleted. The cursor stays on the frame the whole run, as the rule says. Root fix: one runner in the interpreter, one cursor. Leaves the compiled tier as it is (P29 stays). Waits for #192 and #234 (S9, so the top level has a scope node too). About 150 lines in `scope.rs`, `bodies.rs`, `run.rs`. No DESIGN change: the rule already says this.
- (b) **S21: a mode flag.** `run(scope, upto, exit: bool)`: `drain` calls it with exit off. Smallest change, and it does not wait for #234, but it is a symptom fix: one function with two modes, and `drain` still keeps its own list and its own skip rules. I recommend against it.
- (c) **S22: S20 plus a stack of live scopes on the frame.** As (a), and the frame also keeps each live scope (node and cursor) as data, so a `return`, a fault or a cancel ends every live scope from that stack instead of from a Rust error passing back through each `run`. Also removes W68 and the interpreter half of W63/W64, which ›Scheduling, preemption, and cancellation happen at boundaries‹ ("running its live scopes' pending `defer`s") will need. Twice the size of (a), and that rule is "Seed: not yet", in the adaptive layer after v1.0.0. Better as a later step on top of (a).

Recommended: (a), because it removes the root (one runner, one cursor) with the smallest change that does so, and it is what the rule already says. (c) can follow later on top of it.

If you choose (a), no DESIGN wording changes; the issue would start `Solution S20 for W75 (chosen 2026-10-01)` and `Blocked by #192, #234`.
