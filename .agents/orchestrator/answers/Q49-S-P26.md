## The root cause, in plain words

DESIGN says a backend (Cranelift, later LLVM, WASM) is an ordinary identity that carries its own lowering rules:

> ›Backends are identities, and lowering is keyed by them‹: "A backend is an ordinary identity carrying its own mapping from node kinds to emission code. ... Nothing per identity may hard-code one backend; lowering is per backend, per identity." **Why:** "one lowering slot per identity would repeat the mistake of one mutable code field on `+`."

The seed has no backend at all. Lowering is one global Rust map, `LowerTable = HashMap<DyadPtr, LowerFn>` (`src/compile.rs`), from a node's identity straight to a Cranelift function, filled by 23 `cx.lower.insert(...)` lines in 18 identity files. That is exactly the "one lowering slot per identity" the rule rejects. The word "backend" appears once in `src/`, in an error message.

Because no backend holds a rule set, the rule "`+` over `i32` is `add_i32`" has nowhere to live, so it stays in Rust inside `+`'s constructor: `build_op` matches on the operator family and looks the machine op up in tables indexed by the number type (`arith_leaf`, `cmp_leaf`).

## One problem under it (P26)

```
x := i32 1, (x == 1) + 1
```
prints `2` (interpreted, dev at c8a654c). It should be refused, as `true + 1` already is:
```
true + 1
error: this operator cannot compute over these operands
```
A comparison yields `bool` (›A type's `parse` decides what converts into it; unwritten, a value converts only into a type that holds it exactly‹, renamed on 2 October).

The direct cause is W2: `numtype_of` guesses the comparison's type and answers `i32` ("A comparison or logical result is `bool`, physically an i32", `src/identities/mod.rs`). **S1 (#82, already chosen) removes P26.** So W49 has no problem of its own left once S1 lands.

## Solutions I see

**(a) S25, a backend identity now.** Mint a `cranelift` backend in Core; its record holds the rule set; the 23 `lower.insert` lines register on it; `f.compile()` lowers through the backend it is given.
Verdict: right by the letter of the rule, about 20 files of one-line changes, and it clashes with #192 on `compile.rs`/`mod.rs`. But it removes no problem, and with one backend it is mostly a rename of code S3 deletes. Weak.

**(b) S26, machine ops chosen by a rule set.** `add_i32`, `fadd_f64` become identities; one rule per (operator, operand type) fills `+`'s op slot; `build_op`'s `match` on the family and the `arith_leaf`/`cmp_leaf` tables go. Then a new number type is new rules, never an edit to `+`.
Verdict: removes W47 and W45 at the root. But it cannot start now, three things block it (questions 2 to 4 below): #152 is open on the same question, two rules disagree on when the op slot fills, and it is unruled whether the interpreter shares the rule set.

**(c) S27, the backend becomes an identity together with the Logos IR (S3, #164).** Every identity lowers once to the IR, the same for all backends; the `cranelift` backend identity carries the rules from IR operations to machine code. Nothing is built on today's `LowerTable`.
Verdict: fits ›Backends are identities‹ and ›One backend interface‹ ("Anything taking Logos IR and emitting code satisfies one interface") together, and builds nothing that S3 throws away. Cost: W49 stays open until S3, which is only proposed and comes late (after #192, #127). Nothing waits on W49 meanwhile, since S1 removes P26.

## 2. (only for (b)) Two rules disagree on when `+`'s op slot is filled

›Which machine operation an operator is (`+` over `i32` → `add_i32`) is a lowering rule‹: "A rewrite rule ... picks the operation **the first time the node is lowered or run** and stores it in the node's op slot".

›A generic function body is lexed once and built once per set of field types‹: "its op slots **resolve at that construction** as anywhere else", and its Why: "Filling op slots later would give every operator a slot to fill (#69)".

So in `x := i32 1, y := x + 2`, is `add_i32` chosen when `x + 2` is built (parse), or the first time it runs?

- (a) **At construction**, where the types are known; unknown types keep the slot open until they arrive (›Deferral is authored‹). The first rule's wording changes.
- (b) **At first run or lowering**: the slot is written then; this has the run write the graph, which the 28 September ruling (#167, "a run never writes into the graph") forbids.

Recommended: (a), it is what the seed does and what #167 allows.

## 3. (only for (b)) Does the interpreter share the backend's rule set?

›Which machine operation...‹ says the pick "is a lowering, which ›Backends are identities‹ makes a rule set". But the interpreter runs `add_i32` too. Example: `x := i32 1, x + 2` with no `compile` at all still needs `+` over `i32` to mean `add_i32`.

- (a) **One rule set, not owned by a backend**: (operator, operand type) → machine op identity is shared; a backend only says how to emit each machine op.
- (b) **The interpreter is a backend identity too**, with its own copy of the rule set.

Recommended: (a); (b) writes the rule twice, the root W4 is about.
