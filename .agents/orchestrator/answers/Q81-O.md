## Your questions from Q78

**Does `pws.py` open the file every time, or is it cached?** It opens it every time. Each `pws.py` command is a new program: it reads the whole `PWS.json`, does its one job, and a command that changes the graph writes the whole file back. Nothing stays in memory between two commands. Today this is fast: LogosLang's graph has 315 nodes in 0.86 MB, and one command takes 0.15 seconds. It does not stay fast. Problem P85 measured a copy of AI-RCA's graph scaled up to 100,485 nodes: the file was 311 MB, one search took about 25 seconds, and one write about 17 seconds.

**Is there a storage limit on GitHub?** Yes, two hard ones and three recommendations ([Repository limits](https://docs.github.com/en/repositories/creating-and-managing-repositories/repository-limits), [About large files](https://docs.github.com/en/repositories/working-with-files/managing-large-files/about-large-files-on-github)):
- A single file over 100 MiB is refused. Over 50 MiB, git prints a warning.
- One push over 2 GB is refused.
- A repository should stay under 10 GB on disk. The large-files page asks for less: ideally under 1 GB, and under 5 GB is strongly recommended.
- A folder should hold at most 3,000 entries, and folders should nest at most 50 deep.

So one `PWS.json` hits the 100 MiB wall at about 33,000 nodes (about 3 KB per node). At AI-RCA's pace, 495 nodes in its first 6 days, that is a little over a year away. Git keeps every committed version of every file, but when it packs the repository it stores each new version as the change from an older one, so many small edits stay small.

**Many `PWS.json` files of 100 nodes each?** It solves the 100 MiB wall, and a write rewrites only one file of about 300 KB. Two weaker points:
- A search still has to read every file, unless something indexes them (SQLite, below).
- Two agents that add nodes at the same time often write to the same file, and git then has to merge two changes to one file.

One file per node fixes both: a commit shows exactly which nodes changed, and two agents touch the same file only when they edit the same node. 100,000 files need subfolders to stay under 3,000 per folder, for example `W/1/W1234.json`. Either way, the search should not read the files themselves; an index should.

**Read counters, "last agent read" and "total agent reads", and forgetting nodes with a low score?** A good idea for ranking, with two limits:
- The counters belong only in a file on this machine, never in the committed nodes. Otherwise every search would change files, every read would need a commit, and two agents reading one node at the same moment would conflict.
- A node that is still open is never hidden: an open problem, a why under an open problem, a solution not yet done. If a search hid it, an agent would not find it and would add the same problem again, which is the duplicate the search exists to prevent. A closed node (a fixed problem, a rejected why) may sink.

An example of a formula: `score = 0.5 ^ (days since last read / 30)`. A node read today scores 1, one not read for 30 days scores 0.5, and one not read for 60 days scores 0.25. Today `pws.py` already marks a solved cause in search results.

**SQLite?** It fits well as the index. It is a database in one file, built into Python, so nothing needs installing, and it has full-text search with BM25 ranking built in. I checked that the Python on this machine has it (SQLite 3.51.2, BM25 working). Agents do write SQL well. Two changes to your plan:
- SQLite does not live in memory. It is a file on disk, and it is fast because it reads only the parts a query needs. So nothing has to be saved when the PC turns off. A save at shutdown would also be risky: a crash or a power cut skips it, and the work since the last commit is lost.
- Each write goes to the node's JSON file and to SQLite in the same command. The JSON files are what git commits and GitHub shows, and a diff shows each change. The SQLite file stays on this machine (git ignores it), and if it is lost or stale it is rebuilt from the JSON files. It is not committed because it is binary: GitHub cannot show what changed in it, and two branches that both changed it cannot be merged.

Agents should still write through `pws.py`, because it checks the graph's rules, for example that an accepted why has evidence and that ids are unique. Reading with plain SQL would be fine.

**Rust?** Not now. The slowness comes from reading and writing the whole file on every command, not from Python. Rust would read the same 311 MB faster, but it would still read all of it every time. With one file per node and an index, each command reads only what it needs, and Python is fast enough for that. Rust can come later if a measurement shows Python is then the slow part.

**A frontend to view all nodes?** Yes, easy. A small web page served on this machine could list the problems, open one, and show its tree of whys down to the roots, with the solutions and your decisions. It can read SQLite, or the JSON files directly. Nothing else depends on it, so it can come at any time.
