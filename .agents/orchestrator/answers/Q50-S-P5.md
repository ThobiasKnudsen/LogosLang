## The root cause, in plain words, after your Q-44 and Q-46 answers

Some bodies are written in one place and built later: a type's `run` body (built at its first node), and a `type (…)` in a loop or function (built each time the body runs, as you ruled in Q-46). Two functions build them: `construct_run_body` (src/parse/bodies.rs) and `construct_held_type` (src/parse/types.rs).

Where the body was written, the seed keeps only its text and its scope. Everything else happens at the build:
- its **names are looked up at the build**, in the scopes as they stand then, so a name declared *after* the body is visible to it;
- its **`immediate`s run at the build**, so once per build instead of once where written.

What your answers changed: W9 also said "only `construct_run_body` keeps its builds". Under Q-44 and Q-46 that is right, not a defect (a type is new each time its body runs; a `run` body is still built once per set of field types). So W8 ("the held type keeps no build") is no longer a problem, and my first two solutions, S28 and S29, both added that memo.

## The problems that still stand (dev c8a654c, interpreted tier)

**P6 (#230)**, through `construct_run_body`: `u`'s `run` body declares `z`; a `z` written *after* `u` makes it fail.
```
u := type ( a := ?, output_type := type ?, share run = ( z := a, f64(z) ), share parse_rank = 60, share parse = ( tape[0]:type = u, tape[0].a = tape[1], tape[0].output_type = f64, tape.remove(1), tape.is_constructed[0] = true ) ), z := i32 0, x := i32 3, print «{u x}»
```
prints `error: … z is already declared and still in scope` (exit 1). Without `z := i32 0, ` it prints `3.0`.

**P38 (new, I found it today)**, the same thing through `construct_held_type`:
```
for 0..2 ( t := type ( share g := fn () -> i32 ( z := i32 2, z ) ), print «x» ), z := i32 0, print «end»
```
prints `error: … z is already declared and still in scope` (exit 1). Without `z := i32 0, ` it prints `x x end`.

**P5 (#197)**: the `immediate` runs at every build:
```
print «start», for 0..3 ( t := type ( share g := immediate ( print «hi», 1 ) ), print «iter» ), print «end»
```
prints `start hi iter hi iter hi iter end`; Q-46 gives `start hi iter iter iter end`. Its cause is now W77 (draft): the body is only lexed where written, and all of it, the `immediate` too, is parsed at the build.

```
W9  a body built later keeps only its text and scope from where it was written
├─ W10 select looks names up at the build, not at the written point → P6, P38
└─ W77 (draft) the whole body is parsed at the build              → P5
```

## 1. Which solution do you take?

- (a) **S30: resolve the body's names where it is written.** This is #219's "build in part where written" (your Q-28 and Q-29), widened by one step: besides running the `immediate`s there, the part built where written also looks up every name and checks every declaration, at that point. A build later only finishes what needs a call's or a node's types, using the names already found, and never looks in the scopes again. So in P6, `z := a` is checked when `u` is written, when no other `z` exists yet, and the later `z := i32 0` cannot reach it. One change fixes P5, P6 and P38 in both builders. It also fits "one record per name" (4 September): the `z` in `u`'s body is one name, found once.
- (b) **S8 (already proposed on #230) plus #219 as it is.** Store the written point on each held body and make `select` keep only names whose range covers it, at every build; #219 separately moves the `immediate`s. Two changes, and every build still looks names up again, now filtered by the point.

Recommended: (a), because the build then has nothing left to look up, so "a name declared later" cannot happen at all, where (b) keeps the lookup and adds a filter to it.

Rule wording (a) would write, under ›Name resolution is scope-filtered, and shadowing is disallowed‹ (it leans on the "built as far as it can be where it is written" text, which merges to dev with #197):

> - **Ruled (1 October 2026, Thobias, W9):** a body built later, a `fn` body, a type's `run` body or a `type (…)` in a body, has its names resolved where it is written, as part of what is built there (›A generic function body is lexed once and built once per set of field types‹). A build finishes only what needs a call's or a node's types and resolves no name again, so a name declared after the body is never one of its candidates: `u := type ( …, share run = ( z := a, f64(z) ), … ), z := i32 0, x := i32 3, print «{u x}»` prints `3.0`. **Why:** <your words>.

(b) writes no rule: ›Name resolution is scope-filtered‹ already says "the point decides, not the scope alone".
