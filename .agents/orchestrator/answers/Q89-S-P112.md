## 1. Who says that a call hands on a value it made: the function's result type, or its body?
**Decision:** how a call tells a made value from a borrowed one, which also settles whether `-> own @T` exists · **Recommended:** (a) · **Why:** the answer is then written before the body is parsed, so no call ever walks into another function's body

---

### The root cause, in plain words

This is root cause W211 in the problem graph (the file `.agents/orchestrator/PWS.json`, where every problem is traced to its cause). It is the cause under P112, the slow chain you saw on issue 82 (issue 82 is the work on what type each node gives).

When a function's call gives back a pointer or a value with a `free` slot, the caller must know one thing: did the function make that value, so the caller now owns it and must free it, or did it only lend it out, so the caller must not free it? Today two functions with the same written line can answer differently:

```
y := alloc 1 of i32 3,
f := fn () -> @i32 ( alloc 1 of i32 5 ),     f makes its value: the caller owns it and frees it
g := fn (p := @i32 ?) -> @i32 ( p ),          g lends one out: the caller must not free it
```

Both are written `-> @i32`. Only the body tells them apart. This is what DESIGN's rule ›A last value moves out‹ (ruled 25 September 2026) says: a function's last value, when it is made there, moves to the caller, and "the caller knows it owes the teardown, because the parse sees the callee's body at the call."

So the answer exists only once the body has been read. The seed (the Rust implementation) keeps no such answer on the function. Every time it meets a call, it walks into the callee's body again, and through every call inside that body, and through both arms of every `if`. That is the cause.

### One problem it causes

P112, on issue 82's branch:

```
c := i32 1,
h0 := fn () -> @i32 ( alloc 1 of i32 5 ),
h1 := fn () -> @i32 ( if (c == 1) (h0()) else (h0()) ),
h2 := fn () -> @i32 ( if (c == 1) (h1()) else (h1()) ),
… up to h22,
7
```

It prints `7` after 1.01 seconds on the branch, and after 0.01 seconds on `dev`. Each added function doubles the time, because reading `h22` walks into `h21` twice, each of those walks into `h20` twice, and so on: 2 to the power 22 walks. It should print `7` in about the time `dev` takes. Your rule of 9 October 2026, ›Reading a program takes time in step with its size; no walk runs once per path‹, says: "An answer a walk needs again for the same node is kept, not walked again."

### What else it explains

The chain under W211, from the cause down:

- W207: a function's record keeps no answer to "made or borrowed", so a call can only learn it by walking the body.
- W205: the walk re-walks every callee and both arms of every `if`, so it runs once per path (P112).
- W217: the walk stops after 32 calls deep, as a guard against a function calling itself. A long chain with no self-call is cut too, so a value made 32 calls deep (or 10 calls deep for a record such as `bag`) is treated as unknown. P123: `x := f10()` with ten `bag`-returning functions never frees the `bag`.
- W215: a function calling itself, inside its own body, has no answer yet, and no rule says what it gives. `mk := fn (n := i32 ?) -> @i32 ( if (n == 0) (alloc 1 of i32 5) else ( x := mk(n - 1), x ) ), 7` is refused today.
- P117 and P118 (not traced yet, likely the same cause): where the walk gives up, an `if` that makes in one arm and borrows in the other is let through and leaks, and a name bound to a made value owns nothing and leaks.

### The conflict in DESIGN you must rule on (P121)

DESIGN says two different things about how a call hands on a made value:

- ›Gate spelling: words left of `:=`; ownership in the reference type‹: "`-> own @T` hands ownership to the caller. Unmarked is fail-closed: private, immutable, borrow-only."
- ›A last value moves out‹: an unmarked `-> @i32` or `-> array i32` hands on its made last value, "an `alloc`'s owning `@T` included".

Two more rules leave a result's `own` open: ›Left of `:=` stands one name (or regex), with its gate words in front, and nothing else‹ ("Open: a gated return type … Whether the reference words `own` and `share` … keep that place ("unsure", 15 September 2026)"), and ›A gate word stands only where a binding is being filled‹ ("a return type (open, see above)"). The seed refuses `-> own @T` today: "`-> own @T` is not in the seed yet". The option you pick below settles this too.

### The options

- (a) **The result type says it (S58).** A function hands on a value it made only when its line says so, with `own`. The parse checks the body against the line when the function closes. A call reads the answer from the callee's line and never walks its body.

  ```
  f := fn () -> own @i32 ( alloc 1 of i32 5 ),       hands on what it made
  g := fn (p := @i32 ?) -> @i32 ( p ),                lends one out
  h := fn () -> @i32 ( alloc 1 of i32 5 ),            error: this function hands on a value it made: write `-> own @i32`
  mk := fn () -> own array i32 ( array i32 [1, 2] ),  the same for a type that fills `free`
  ```

  This removes W207, W205, W217 and W215: a function's call to itself is answered by its own line, which is written before its body. P112, P117, P118 and P123 go. The seed gets smaller: the walk into other bodies, the 32-deep guard and the "unknown" answer are deleted. A block keeps ›A last value moves out‹, since its body is right there: `x := ( a := array i32 [1, 2], a )` still makes `x` the owner. The cost: you write `own` on every function that hands on what it made, and about 20 test lines change (`-> array i32 ( array i32 [1, 2] )` becomes `-> own array i32 ( … )`). It reverses part of your 25 September 2026 ruling (›A filled `share free` is the value's teardown; one name owns each value‹, "second of three options"), whose reasons include "existing code keeps working". Until that day DESIGN said what (a) says: "a bare `-> @T` returning an owned place stays the checked error" (DESIGN_HISTORY.md, under ›Three fail-closed ownership rules, and `-> own @T`‹). It is how Rust does it: `fn mk() -> Box<i32>` owns and `fn get(&self) -> &i32` lends, and a caller never looks at a body.

- (b) **The parse reads the body once and remembers (S59).** Nothing changes in what you write: `-> @i32` may hand on a made value, as today. When a function closes, the parse works out once whether its calls make or lend, and keeps that answer on the function, the way it already keeps the list of outer names a body reads (›A call is a use of every outer name the callee's body reads‹). A call reads the kept answer. `-> own @T` is deleted from DESIGN.

  This removes W207, W205 and W217, so P112, P117, P118 and P123 go, with no test changes. Its costs: a function's call to itself inside its own body (W215) still has no answer, so it needs one more rule, which I would ask you in the next round (refuse such a call where its answer is needed, or assume an answer and check it when the function closes). A body built later than where it is written (a generic function built per set of field types) has no answer until it is built. And it keeps a copy worked out from the body. On 8 October 2026 (Q72) you declined a stored copy of what an `if` or a block gives ("since the information already exists", and "a program that needs it faster keeps its own cache"); the risk put to you then was that a stored copy must be updated after every rewrite of the body, and a missed update goes unnoticed. Here a missed update would silently change who frees the value in every caller.

- (c) **Both (S60).** `-> own @T` may be written, and is then checked; where it is not written, the parse works the answer out as in (b). This keeps every cost of (b) and adds the check of (a), and a reader of `-> @i32` still cannot tell whether it lends. I recommend against it.

- (d) **Only make the walk smarter (S61).** Keep the design, but walk one arm of each `if` and tell a self-call by the functions already being walked instead of a depth count. The doubling goes, but each function's close still walks every function below it, so the chain's time grows with the square of its length (675 walks at 10 functions). That breaks your 9 October rule, so I recommend against it.

Recommended: (a), because the answer is then a written fact on the function's line, known before its body is read, so no call walks into another function, a self-call and a body built later need no new rule, and nothing is kept that a rewrite could leave stale.

Both (a) and (b) leave two smaller problems that are not this cause: P113 (a long `else if` chain is slow, because an `if`'s answer is worked out again at each level) and P122 (each function's close starts the same walk 8 times). They get their own why round.

### The exact wording each choice writes in DESIGN.md

Picking (a) or (b) also approves its wording below. The dates and question number are filled in by the orchestrator.

**If (a):**

- ›A last value moves out‹, the rule text becomes: "A block's last value, when it is a place the block owns, moves to whoever takes the value, an `alloc`'s owning `@T` included: `x := ( a := array i32 [1, 2], a )` makes `x` the owner. A function hands on a value it made only when its result type says so, with `own`: `mk := fn () -> own @i32 ( alloc 1 of i32 5 )`, and `mk := fn () -> own t ( a := array i32 [1, 2], a )` with `t := array i32`. The parse checks the body against the result where the function closes: under `-> own`, the last value is made or moved in every arm; without it, the last value is a borrow or a value with no end, and `fn () -> @i32 ( alloc 1 of i32 5 )` is the checked error "this function hands on a value it made: write `-> own @i32`". A call reads whether it hands on a made value from the callee's written result, never from its body, so a function's call to itself is answered while its body is still open. A `return` of an owned place before the last line stays the checked error; the teardowns of the scopes it leaves run on the way out."
- Its **Why** becomes: "the caller knows it owes the teardown from the line of the function it calls, as a block's binder sees the block's last line; a call needs no walk into its callee, so a chain of calls reads in time in step with its length (›Reading a program takes time in step with its size; no walk runs once per path‹), and a call whose callee is still open or not built yet has its answer."

- ›Left of `:=` stands one name (or regex)…‹: the Open line becomes "Ruled: `own` keeps its place in a result type, `-> own @T` (›A last value moves out‹); `share` in a result waits for ›Shared ownership through `share` (direction)‹."
