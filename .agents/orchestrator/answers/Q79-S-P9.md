## The root cause, in short

**What it is.** In Logos a value often "lands" in a place that has a type. Eight places in the seed do this: a call's argument, `x = v`, a write through a pointer `p@ = v`, a hashmap write `m[k] = v`, an operand on the tape, a record constructor's field, a write into `tape[0]` inside a `parse`, and a function's last expression (its "tail"), which lands in the type written after `->`. Each of the eight checks the value with its own copy of the check, in Rust, around a helper called `check_store_type` (`src/identities/mod.rs`). The copies have drifted apart. This is root cause W15 in the problem graph.

**One problem it causes.** The function tail's copy (`commit_tail`) never checks a value that already has a type. So this program runs and prints a wrong number:

```
f := fn () -> i32 ( f64 2.5 ), f()
# prints: 0        (the low 32 bits of the f64, read as an i32)
```

The same value into the same place type at a call's argument is refused, as it should be:

```
g := fn (a := i32 ?) -> i32 ( a ), g(f64 2.5)
# error: these types do not match
```

On the compiled tier (`f.compile()`) the first program fails with an internal "Verifier errors". And `f := fn () -> @i32 ( i32 5 ), p := f(), p@` crashes the seed (a segfault, exit 139), because the number 5 is handed back as an address. Issue #198 lists about forty such programs; all of them come from the one missing check at the tail.

## 1. Which fix to take for the landing check
**Decision:** which solution becomes the fix for W15 (issue #198) · **Recommended:** (a) · **Why:** it removes the eight copies and makes your 2 October rule true at every landing in the same change

---

Two solutions are recorded in the problem graph. Both replace the eight copies with one function, `land(value, place_type)`, which every site calls. They differ only in what `land` accepts.

S11 was written on 29 September, before you ruled Q-63. It accepts a value only when its type is exactly the place's type. That is the rule you replaced. It would keep refusing `x = f32 9`, and it would newly refuse `f := fn () -> i64 ( i32 5 ), f()`, which prints `5` today and is right under your rule.

S36 is new. `land` asks the place's type, as your rule says: a value of the same type passes; a plain number is converted exactly by the number type's own definition (as today); a value whose type lies inside the place's type is converted, by building the same node that the written conversion `T(value)` builds today; anything else is refused. It is also what each `if` arm uses, since your Q-61 ruling says each arm converts to the type needed where the `if` stands. The "lies inside" test is one Rust function beside the number types' parse in `numtype.rs`, worked out from each type's sign, width and whether it is a float, not a hand-kept table.

Under S36:

```
f := fn () -> i32 ( f64 2.5 ), f()               # error: these types do not match (f64 does not fit in i32)
f := fn () -> @i32 ( i32 5 ), f()                # error: these types do not match (no more segfault)
f := fn () -> f64 ( u32 4000000000 ), f()        # 4000000000.0   (today: 1.9762625834e-314, problem P90)
mut x := f64 0.0, x = f32 9, x                   # 9.0            (today: refused)
mut x := f64 0.0, x = if (1 > 0) (f32 1.5) else (f64 2.5), x   # 1.5   (today: refused)
```

- (a) **S36: one `land` that converts what lies inside the place's type.** The issue for the work is #198, rewritten to S36. Its cost is a little more than S11: the "lies inside" function and the conversion node, plus the seed's tests that today expect a widening to be refused, which change to expect the converted value. Issue #212 (W19) and issue #242 (the operators' conversion, `i32 1 + i64 2`) then reuse `land` instead of writing their own.
- (b) **S11: one `land` that accepts only the exact type.** The copies go, and `fn () -> i32 ( f64 2.5 )` is refused, but the seed keeps the rule you replaced, and widenings like `x = f32 9` stay refused until a later change rewrites `land` again.
- (c) **Something else.** Write what you see instead, and I will assess it the same way.

Neither fix covers a parameter written `?` or bare, `fn (a) -> i32 ( a )`. That needs a function body built once per set of argument types, which is issue #202 (blocked by #127, "a function is a type"). Once that lands, each built body goes through `land` with nothing more.

Recommended: (a), because (b) would build a second time what your 2 October rule already decided, and would turn programs that are right today into errors.

## Decided
These are my own decisions. Each follows from your rule above, so I did not ask them as questions. Answer "ok" to accept them, or write what you want instead.
- **An integer lies inside a float when the float holds every value of the integer exactly.** So `i32` lies inside `f64`, and `f := fn () -> f64 ( i32 5 ), f()` gives `5.0`. `i32` does not lie inside `f32`, because an `f32` holds every whole number only up to 16,777,216. `i64` does not lie inside `f64`. `u32` lies inside `i64`, and `i32` does not lie inside `u64`, because a negative `i32` has no `u64`. This rests on your Q-63 words in the rule, "the value's type lies inside that type, so nothing is lost", and on your Q-20 words "i32 is a subset of i64": one type lies inside another when every value of the first is a value of the second.
- **A `bool` lies inside no number type, and no number lies inside `bool`.** So `f := fn () -> i32 ( true ), f()` and `f := fn () -> bool ( i32 5 ), f()` are refused where `f` is defined; today the first prints `1` and the second `true`. This rests on the same rule: a value converts only when "that type's `parse` takes it", and "A type whose `parse` says nothing for it refuses it". Nothing in DESIGN makes `true` a number, and the written conversion `i32 (true)` is already refused ("a conversion takes exactly one numeric value").
