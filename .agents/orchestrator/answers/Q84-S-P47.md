## What is wrong, in plain words

A type's `parse` is the Logos code that runs when the type's name appears in a program. It builds the node for that appearance. Inside it, `tape` is the row of cells around the appearance, and `tape[0]` is the node being built. `tape[0].lhs` is a field of that node.

DESIGN.md already says what such a field holds while the parse runs. The rule ›A field is filled at run, per evaluation; its type decides how the operand is used‹ says: "At parse it is a slot in the node holding the operand node itself, `tape[0].lhs = tape[-1]`, eight bytes whatever the operand's type." The rule ›Reading a path runs nothing‹ says that a name, literal or place reached this way "stands as itself".

The seed (the Rust implementation) does something else. When a field is declared with a number type, such as `lhs := i32 ?`, the seed reads `tape[0].lhs` in the parse by running the node the slot holds, to get its number. This program shows it:

```logos
pr := type ( lhs := i32 ?, rhs := i32 ?, output_type := type ?, share run = ( lhs + rhs ), share parse_rank = *.parse_rank + 1, share parse = ( tape[0].type = pr, tape[0].lhs = tape[-1], tape[0].rhs = tape[0].lhs, tape[0].output_type = i32, tape.is_constructed[0] = true, tape.remove(-1) ) ), f := fn (x := i32 ?) -> i32 ( x pr ), f(4)
```

It prints `1078493284` on one run and `-1958485916` on the next. It should print `8`: `rhs` should hold the same node as `lhs`, which is the parameter `x`, and `4 + 4` is `8`. At the top level, with `x := i32 3, x pr`, it prints `6`, which is right.

The number is garbage because the parse runs the read of `x` while it is building `f`'s body. No call of `f` exists at that moment, so `x` has no value. The seed should stop with its checked error "a function's local was read outside any call". Instead it reads the memory of the parse's own call, at the spot where `x` would be.

## Why it happens

The why agents found four causes. One fix should serve them all:

- When the seed reads a local of a function, it reads it from the call that is running right now, whatever function that call belongs to. A running call does not remember which function it is a call of. This holds in the interpreter and in compiled code.
- The seed decides in three separate places which parts of what a parse writes are kept as graph (run later, when the node runs) and which run at once, in the parse.
- The seed has no way to say "this is a node that will give an `i32` when it runs". A read of a field either gives the node as a bare address, or gives an `i32`, which it can only get by running the node.
- DESIGN says when a function body and a type's `run` body are built (›A generic function body is lexed once and built once per set of field types‹), but not when a `parse` body is built. The seed builds it once, where the type is defined, before any appearance hands it a node.

## 1. A `?` field of the node being built, used in the parse
**Decision:** how the parse may use a field declared `?` before the node exists · **Recommended:** (a) · **Why:** one check-then-use rule for everything a parse holds, and the parse body is still built and checked once, where it is written

---

Both options fix all four causes the same way for a field with a declared type. Inside a parse, `tape[0].lhs` is the node the slot holds, and it is never run there. Writing it into another field copies the node, so the first program prints `8`, in the interpreter and in compiled code. A field declared `lhs := i32 ?` is read as an `i32` when the body is built, because the parse checked that type when it wrote the field.

The two options differ only for a field declared with a bare `?`, which has no type until the parse writes one. In the second program, the field `n` is `?`, and `tape[0].n * 2` has to know what `n` holds to know which `*` it is.

- (a) **Check it first, as a tape cell is checked.** The parse body is still built once, where the type is defined. A `?` field read there is just "a node", as an unchecked `tape[k]` is today. To use it as a number, the parse checks it first, the same way it already checks a tape cell. The second program would be written with `if tape[0].n.type ⊆ u64 ( tape[0].m = tape[0].n * 2 )`, and then it prints `6`. Without the check, it is an error where the type is defined. `.type` works without a check, so the third program prints `rational_number`. This would be recorded at ›A tape read checked against a number type reads as that number‹ as:

  > **Ruled (<the date of your answer>, Thobias, Q84):** inside a parse, a field of the node being built, `tape[0].f`, is read as a tape cell is: it is the node its slot holds, never run there. Its type is the field's declared type; for a `?` field it is a node until a check narrows it, as a cell's check does: `if tape[0].n.type ⊆ u64 ( tape[0].m = tape[0].n * 2 )`. Written into the node, it and anything built over it are kept as graph and run when the node runs, so `tape[0].rhs = tape[0].lhs` copies the operand node. Read for its value while the parse runs, only a constant gives one; anything else is the checked error. **Why:** <your words>.

- (b) **Build that part at each appearance.** The parts of a parse body that read a `?` field are built again at every appearance of the type, once the field holds its node. The second program prints `6` as written, with no check, and the third prints `rational_number`. The cost: the parse runs slower each time the type appears, and a mistake in such a part shows only where the type is used, not where it is defined. It also needs a way to build part of a body later, which is unfinished work elsewhere in the seed, so this fix would wait for that work. This would be recorded at ›A generic function body is lexed once and built once per set of field types‹ as:

  > **Ruled (<the date of your answer>, Thobias, Q84):** the rule holds for a type's `parse` body too. A part of it that reads a `?` field of the node being built is built at each appearance, once the slot holds its node, so `tape[0].m = tape[0].n * 2` is typed by what `n` holds there; the rest is built where it is written. Inside a parse, `tape[0].f` is the node its slot holds, never run there; written into the node, it and anything built over it are kept as graph, so `tape[0].rhs = tape[0].lhs` copies the operand node. **Why:** <your words>.

Recommended: (a), because a parse already checks a tape cell before it uses it as a number, and (a) uses that same rule for the fields of the node it builds. There is one rule to learn, and the parse body is still checked where it is written.

## Decided
These are my own decisions. Answer "ok" to accept them, or write what you want instead.
- **An older proposal for this code is replaced.** A proposal written earlier on GitHub issue 203 (the issue about the three places that split "kept as graph" from "run at once") says a read of `tape[0].lhs` in a parse "runs the operand node the slot holds". That read is exactly what makes the first program print garbage, and DESIGN says the opposite: ›A field is filled at run, per evaluation‹ ("At parse it is a slot in the node holding the operand node itself") and ›Reading a path runs nothing‹ ("a name, literal or place stands as itself"). The rest of that proposal, one way to place what a parse writes instead of three, is kept in both options above. So the option you pick replaces the old proposal on issue 203, and no new issue is opened.
- **A function's local is read only in a call of that function.** The fix also makes each running call remember which function it is a call of. A read of a local then compares the two, and gives the checked error "a function's local was read outside any call" when they differ; compiled code makes the same comparison when it is compiled. This rests on ›A scope lays out its declarations; a use reaches the offset through its binding‹: a function body's names have an offset in "a call's frame for a function body", and "the base of the second is the value's or the call's", so `x` is read in a call of the function that declares it. After question 1's fix the first program no longer reaches this read, but without the check the next mistake of the same shape would again read another call's memory and give a wrong number or a crash. The cost is one pointer comparison per local read in the interpreter, and none in compiled code. It comes first, as the first part of the same fix.
