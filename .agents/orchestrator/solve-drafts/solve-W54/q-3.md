Since Q76 was asked, issue #82 landed, and the three problems Q76 showed are fixed: `x := i32 1, a := x == 1, a` now prints `true`, and `(x == 1) + 1` is refused. ## The root cause, in plain words

The seed has **two ways to read a node**, and they disagree:

- `place_layout` reads a value that sits in a named place, by the value's type.
- `read_kind` reads every other node by the **kind byte**: a small number at the start of every type's record, chosen from a fixed list in Rust (`i32` is 2, a text is 11, and so on).

For three types the two give different answers, so three plain programs fail (dev 3d0655b, interpreted):

```
[1, 2]          run error: this node was built with no operation to run
s := «a», 0     run error: a record, text or hole is not read as one value; read a field or take its address
r := 1/2, 0     run error: a literal here has no exact value in the type it lands in
```

The first should give the bracket's node. The second should hold the text, as `x := 5, n := x:name, n` already does (it prints `x`). The third should hold one half, since DESIGN says `1/2` is a `rational_number` (›A plain number is a `rational_number`, and a number type's definition converts it‹).

**Why `read_kind` still exists.** A type's record does not state four things a read needs, so Rust fills each one in by the kind byte:

1. **Which fields a type has** (root cause W54). `identities/type.logos` names five fields: `parse_rank`, `associativity`, `parse`, `run`, `free`. The rest (`scope`, `fields`, `size_bytes`, the cached `@T`, `extent`) exist only as byte positions in Rust. You can see it: `type.size_bytes` and `pt.fields` are both "this read does not fit the node's type", while `type.parse_rank` prints `92.0` from a Rust byte position.
2. **Where a type's operation is** (root causes W304 and W305). `+` keeps its machine operation (`add_i32`) in an `op` word inside each node, because operations do not mint yet (issue #242). `scope`, `if` and `return` keep theirs in each node too, because a type's `run` can hold only a body written in Logos, never one written in Rust. The `op` word of `[1, 2]` is empty, hence "no operation to run".
3. **How a text or a `[…]` sits in a place** (root cause W300). DESIGN says a value of a type that a Logos `parse` builds, such as an array, is its node's address (›A value of a type built by a Logos `parse` travels as a pointer‹). It says nothing for a text or a `[…]`, whose types the seed builds in Rust.
4. **What a plain number is** (root cause W302). The seed reads a number nothing converts as an `i32`, a stand-in for issue #214. `1/2` has no `i32`.

**The whole fix in one sentence:** a node is read through its type's record and nothing else, so `read_kind` and its list of kinds go.

## 1. Do you take the whole fix?
**Decision:** how far the fix goes · **Recommended:** (a) · **Why:** it removes the second way of reading, which is the root cause, and its first slice is only the rule

---

- (a) **The whole fix, in this order.** Each step removes one of the four gaps above:
  1. `type.logos` declares every field a type's record holds: `parse_rank`, `associativity`, `parse`, `run`, `free`, `print`, `scope`, `fields`, `size_bytes` and `extent`. What only one kind of type needs becomes a `share` member of that type's own body: a pointer type's `pointee`, an operator's `arity` and `roles`. Rust then knows only the layout of `type` itself, which DESIGN allows (›The dyad describes itself down to one fixed point‹: "whose layout is the seed's only built-in knowledge"), and a test checks it against `type.logos`. (Solution S23.)
  2. Operations mint, and `+` keeps `add_i32` on its mint for `i32`, not in each node. You already ruled this on 2 October (Q-59, Q-61); it is issue #242. (Solution S96.)
  3. A core type's `run` may be written in Rust, so `scope`, `if` and `return` keep their operation on the type. Question 3 asks this. (Solution S93.)
  4. A text and a `[…]` are their node's address, like an array. Question 4 asks this. (Solution S94.)
  5. The `i32` stand-in for plain numbers goes, after the step that converts a number where it lands (issue #198). (Solution S95, issue #214.)
  6. The kind byte itself goes last (issue #101).

  Then `type.size_bytes` reads, `[1, 2]` is a value, `s := «a»` holds the text, and `r := 1/2` holds one half. It is big: about 70 places in Rust read the kind byte or the record's byte positions. It runs alone in `src/identities`, one step at a time.
- (b) **The rule only, for now (solution S24).** Write the rule and complete `type.logos`, and leave the seed as it is. This touches no code, but all three programs above keep failing, and the seed keeps a second copy of the shape that nothing checks.

Recommended: (a), because each step removes a problem you can run, and the first step is just the rule.

## 2. What does `t.fields` give? (DESIGN has this open)
**Decision:** what reading a type's fields from Logos returns · **Recommended:** (a) · **Why:** `size_bytes` already needs this list, and it is your website loop

---

Your website's showcase walks a type's fields:

```
pt := type ( a := i32 ?, b := i64 ? )
pt.fields.length                 u64 2
for f in pt.fields ( print «{f:name} {f.type}» )
a i32
b i64
```

- (a) **The list of the type's per-value fields, as their bindings, in the order they are written.** `share` members are not in it. `f:name` is a field's name and `f.type` is its type. The list points at the bindings and copies no names, as ›Field names live in the shared name index, not on the type‹ asks. It is also exactly the list `size_bytes` adds up.
- (b) **Leave it open.** `type.logos` still declares `fields`, but reading it from Logos waits.

Recommended: (a), because `size_bytes` already needs this list, and walking it is what you wanted on the website.

## 3. May a core type's `run` be written in Rust, as its `parse` already may?
**Decision:** where `scope`, `if` and `return` keep their operation · **Recommended:** (a) · **Why:** the operation then sits on the type, where DESIGN reads it, and a Logos version can replace it later

---

DESIGN says how a node runs (›Execution is function application: to evaluate a dyad, read its type; run a `fn`, run a type's `run`, else it is data‹): read its type; if the type has a `run`, run it; else the node is data. A core type's `parse` may already be written in Rust (›The constructors drive the tape‹, Seed: "the core `parse` is `native`"). Its `run` may not: the record has room only for a body written in Logos. So the seed puts the operation of `scope`, `if` and `return` into a word inside every node instead, and a type with nothing to run, such as `[…]`, gets an empty word.

- (a) **Yes, as with `parse`.** A core type's `run` holds its operation written in Rust. Every `( … )` runs the operation of the type `scope`, and no node carries its own. `square_brackets` has no `run`, so `[1, 2]` is data, a value, and no longer an error.
- (b) **No, every `run` is written in Logos.** That is the goal of ›Still to be written in type.logos‹ ("the definition of `type` must define what `run` and `free` do"). But `scope`, `if` and `return` are what Logos itself runs on, so they cannot be written in Logos yet, and until then they keep their word in each node.

Recommended: (a), because it puts the operation where DESIGN reads it now, and each one can later be replaced by a Logos `run`, as a `parse` can.

## 4. What is a text or a `[…]` when it stands as a value?
**Decision:** how a text and a bracket sit in a place · **Recommended:** (a) · **Why:** one rule for every value kept in its own node, and it is what the seed already does for `x:name`

---

- (a) **Its node's address, eight bytes in a place, as for an array.** `s := «a»` holds the address of the text's node, `f(«a»)` hands that address to `f`, and `[1, 2]` read whole is its node. This makes the rule for arrays the rule for every value kept in its own node, whoever builds its type. Issues #213 (text) and #195 (`[…]`) already expect it. What such a value prints stays issue #174's question.
- (b) **Not a value.** A text or a `[…]` may only be handed to a call or read through a field; `s := «a»` and `[1, 2]` stay errors, now by rule.

Recommended: (a), because a text already reads this way through a place (`n := x:name, n` prints `x`), and (b) would refuse `main(«hello»)`, which `--help` shows.

## 5. When does a backend become an identity? (root cause W49)
**Decision:** when the Cranelift backend becomes an identity · **Recommended:** (b) · **Why:** nothing waits on it, and (a) builds on code #164 replaces

---

A **backend** turns Logos into machine code; the seed has one, Cranelift. DESIGN says a backend is an ordinary identity carrying its own rules (›Backends are identities, and lowering is keyed by them‹). The seed has no backend identity, only one Rust table from each identity to its Cranelift code. No problem you can run depends on this.

- (a) **Now (solution S25).** Make a `cranelift` identity whose record holds that table. With one backend this is mostly a rename, and issue #164 (a small typed Logos IR between the graph and every backend) rewrites the same code later.
- (b) **Together with the Logos IR, #164 (solution S27).** Every identity is turned into the IR once, the same for every backend, and the `cranelift` identity carries the rules from IR operations to machine code. Nothing is built on today's table.

Recommended: (b). Which machine operation `+` gets is no longer part of this question: since your Q-61 ruling it sits on the mint (#242).

## Decided (orchestrator)
- **The plain number (W302, S95, #214).** ›A plain number is a `rational_number`‹ already decides what `1/2` is; only the order is left. Dropped too early, the stand-in would take every function with a plain number off the compiled tier, since the compiler refuses rational operations ("Rational operations and places are interpreted only", `src/compile.rs`). So it goes after #198 (one landing step) and #242 (a number's conversion built as the mint's field while parsing). Then no function that compiles today stops compiling, and a function holding a number that lands nowhere typed, such as `r := 1/2` inside it, runs interpreted until rationals compile; today it fails on both tiers. #214 already says "Blocked by #198".
- **Q76's question 4 (when the kind byte may go).** #242 moves the choice of `add_i32` onto the mint (Q-61), which was the byte's second job, so the byte (#101) waits for #242 and for no new rule set. Q76's solution S26 (machine operations chosen by a rule per operator and type) is what Q-61 and #242 already are.
- **Q49's question 2** (is `+`'s machine operation chosen at parse or at first run?) is answered by Q-61 at ›Which machine operation an operator is (`+` over `i32` → `add_i32`) is a lowering rule‹.
- **The renamed heading.** `PWS.json` names ›Still to be written in type.logos; reflection of fields is open‹ for W54 and S23; the orchestrator updates those when it writes the rule.
