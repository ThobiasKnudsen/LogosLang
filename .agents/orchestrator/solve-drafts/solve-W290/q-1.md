## 1. Which fix for a bracket inside a call's brackets
**Decision:** how the seed keeps a bracket's own lines, and how far the fix goes now · **Recommended:** (a) · **Why:** it fixes every wrong answer found, costs no speed, and is a small change

---

**What goes wrong.** In Logos every `( … )` is a scope: a list of lines whose value is its last line (DESIGN ›A scope's value is what it evaluates to…‹: "Every `( )` is a scope that produces a value"). So in `g((i32 4, i32 5))` the function `g` gets one argument, the inner bracket, whose value is `5`. The seed gets this wrong, on both tiers (the interpreter and compiled code):

```
g := fn (b := i32 ?) -> i32 ( b ), g((i32 4, i32 5))
run error: a call's argument count does not match its function      (should print 5)

g := fn (b := i32 ?) -> i32 ( b ), g(( y := i32 1, y + 4 ))
1:60: error: this gives nothing, and a value is needed here         (should print 5)
```

**Why it happens (root cause W290).** When a bracket holds only one line, the seed throws the bracket away and keeps only that line. This is a shortcut the seed takes on purpose, and DESIGN lists it as a known stand-in (›The seed's tape shape…‹: "A one-expression bracket is unwrapped to its expression"). It lives in `parse_block` (`src/parse/bodies.rs`) and in the constructor of `(` (`src/identities/paren.rs`). So in `g((i32 4, i32 5))` the call's own bracket vanishes, and what is left is the inner bracket `(i32 4, i32 5)`, which looks exactly like the call `g(i32 4, i32 5)`. The code that collects a call's arguments (`args_of`, in `src/parse/driver.rs`) then finds two. That `args_of` decides by the kind of node is a second root cause, W289, which follows from this one.

**Everything it breaks.** Besides the two programs above (problem P149 in the graph), I found four more with the same cause, on both tiers at commit 2a081ef. The last two use `tests/fixtures/scope_cell_lines.logos`, where `first` is a type written in Logos whose parse takes the first line of the bracket to its right (`tape[1].dyads[0]`):

```
x := i32 ((i32 4, i32 5)), x     error: a conversion takes exactly one numeric value   (should be 5)
x := dyad ((i32, 5)), x          5        (should be an error: one argument, not two)
first (i32 7)                    error: this node is not a scope                       (should be 7)
first ((i32 1, i32 2))           1        (should be 2, the inner bracket's value)
```

The last one is a silent wrong answer.

**Related root causes.** None decides the same thing. Two touch the same code: W28 (the seed's built-in constructors read what follows them through the parser's text position instead of the tape; its proposed fix S17 starts with `(`), and W12 (five separate readers of a scope's lines; its proposed fix S9 makes `parse_block` the one reader). A fix here changes a few lines in the same functions, not the same decision. No fix was proposed for W290 before.

- (a) **The bracket keeps its own scope (S90).** The `(` keeps the scope it opened on its tape cell, next to its value. Everything that reads a bracket as a bracket reads that scope's lines: a call, a number conversion like `i32 (…)`, `dyad (T, v)`, a member call like `p.m(…)`, and `tape[k]` in a parse written in Logos. The seed's built-in operators still read the one line, so `(x + 2) * 3` is built and runs exactly as today. All six programs above give the right answer. Speed does not change: the seed already makes that scope for every bracket and then drops it. Size: small, about 60 lines across 9 files, a few lines in most. What stays: inside the built-in operators, `(x + 2)` still stands as `x + 2` and not as a scope, which only shows when a program walks its own graph (`b:start.rhs.lhs`).
- (b) **Remove the shortcut entirely (S91).** `(` always leaves a scope, for every reader, as DESIGN says. Then every built-in operator gets a scope where today it gets a line, so all of them, the early folding of `(2 + 3) * 4` into `20`, and both the interpreter and the compiler must learn to read through a scope of one line. It fixes the same six programs and the stand-in leaves DESIGN. Cost: large, across many files, not measured, and each bracket may cost a little run time in the interpreter. No known problem needs it, and it can still come later, since (a) already keeps the scope.
- (c) **Keep a bracket only around another bracket (S92).** The shortcut skips a one-line bracket whose line is itself a bracket. One condition, the smallest change. It fixes five of the six, but not `first (i32 7)`, and the argument count still depends on the kind of node. It patches the symptom, not the cause.

Recommended: (a), because it fixes all six wrong answers, costs no speed, and is a small change that (b) can still build on later.

## 2. (orchestrator) What `tape[k]` gives a parse written in Logos for a one-line bracket
**Decision:** whether `tape[1]` of `t (x + 2)` gives the bracket's scope or its one line `x + 2` · **Recommended:** (a) · **Why:** DESIGN ›A bracket goes to the call whole‹ says "the cell a `(` lands is a `scope`"

---

Under answer 1 (a), a parse written in Logos must read the bracket's scope for `first (i32 7)` to work.

- (a) **`tape[k]` gives the scope.** `first (i32 7)` gives `7`. A Logos operator with a bracket on its right, like `^` in `identities/power.logos`, then holds a scope as its right side; the seed already gives a scope the type of its last line (`read::output_type`), and the build checks `^` on both tiers. A write `tape[k] = …` to that cell replaces the scope too.
- (b) **Only `tape[k].dyads` reads the scope; `tape[k]` stays the line.** Then `tape[1].dyads` works while `t := tape[1], t.dyads` is refused: one cell read two ways.

Recommended: (a), because DESIGN already says what the cell is, and (b) makes one cell give two answers.

## 3. (orchestrator) The stand-in line in DESIGN under answer 1 (a)
**Decision:** the new wording of one stand-in line at ›The seed's tape shape (#60, #121) and its remaining stand-ins‹ · **Recommended:** (a) · **Why:** it states what the seed then does; no rule changes

---

Today the line reads: "A one-expression bracket is unwrapped to its expression, so the bracket a `(` landed is marked on the cell rather than read off the scope type."

- (a) **New wording:** "A one-expression bracket stands as its expression for the seed's own readers of a value; the cell keeps the scope the `(` landed, and every reader of the bracket reads that scope's lines: a call, a conversion, `dyad (T, v)`, a member call, and `tape[k]` in a parse."

No new rule is needed: ›A bracket goes to the call whole‹ already says "One rule for every bracket: lines are operands", which is what makes `g((i32 4, i32 5))` one argument.
