## What this is about

One problem found in the review of issue 82 (the issue that made a node's value read by its type, merged 9 October) led to three root causes. Each is a gap or a disagreement in DESIGN.md about who owns a value, that is, whose end runs the value's `free`. I hold all three, so one round answers them together.

Words used below:
- A value is **made** when it is just created or moved: `alloc 1 of i32 5`, `bag(3)`, `move a`, or a call to a function whose result says `-> own`.
- A value is **borrowed** when it is read from a name that keeps owning it: in `b := a`, `b` borrows and `a` still owns.
- **Hands on**: a function hands its result to the caller, who then owns it. Since your answer to Q89 (9 October), a function hands on a value it made only when its result says so: `mk := fn () -> own @i32 ( alloc 1 of i32 5 )`.
- `bag` is the test type `bag := type ( mut n := i32 ?, share free = ( print «freed {n}» ) )`, whose `free` prints `freed` and its number.

The problem (P143 in the graph), on `dev` today. Both functions hand on a value made by an early `return`, and both say `-> own`:

```
mk := fn (c := i32 ?) -> own @i32 ( if (c == 1) (return alloc 1 of i32 3), alloc 1 of i32 4 ), x := mk(1), print «{x@}»
  error: a `return` cannot hand ownership out yet; make it the function's last value, which moves out to the caller

<bag>, mk := fn (c := i32 ?) -> own bag ( if (c == 1) (return bag(3)), bag(4) ), x := mk(1), print «got»
  got
  freed 3
```

The pointer one is refused and the record one works. One rule should decide both. The same family has three more problems: a value made in a call's brackets is never freed (P4, `f(box (1, 2))` prints `after` and no `free`), a type's `run` whose `return` makes a value and whose last line borrows one never frees the made one (P142), and a `-> void` function that returns a made value never frees it (P141).

Related work, so you can place it: your Q89 choice (solution S58, `-> own` on the result) is the rule these questions extend; your Q-39 choice (solution S19, no `own ?` on a name declared inside a function) is next to it; the NULL form of a record (root W85) and "a value lands in a place of its type" written at eight places (root W15) each have their own solution agent, and touch the same code but not the same decision.

## 1. May a `return` hand on a value it made? (root W267)
**Decision:** whether a `return` under `-> own` hands on a made value as the last value does · **Recommended:** (a) · **Why:** your Q89 rule then decides every way out of a function, and the reason for refusing is gone

---

DESIGN.md does not say. Rule 3 of ›Three fail-closed ownership rules, and `-> own @T`‹ opens its one door to the last value only: "rule 3 has one door: `-> own @T` … hands the function's last value to the caller". Rule 3's reason was that "a call hides its body behind a return type that cannot yet say it transfers ownership". Since Q89 the return type can say it: `-> own`. ›A last value moves out‹ checks only the last value against `-> own`, and refuses only "a `return` of an owned place", which `return alloc …` and `return bag(3)` are not. So the seed checks a `return` twice, once with an old test that knows only pointers and once with the new `-> own` check, and the two answers differ (above).

- (a) **Yes, every `return` counts as a result** (solution S81): a function's last value and every `return` are its results, and its written result decides them all the same way. Under `-> own @i32`, `return alloc 1 of i32 3` and `return move a` hand the value on, so the first program would print `3`. Without `own`, a `return` of a made value gets the same error a made last value gets: "this function hands on a value it made: write `-> own @i32`". `return a`, where `a` is a name the function itself owns, stays an error: write `return move a`. A type's `run`, which has no `->` to write `own` in, reads its "hands on" mark from its last value and every `return` together, so P142's `run` (a `return` that makes, a last line that borrows) is refused, as your Q72 refuses an `if` whose arms make and borrow. The code change is small: the old pointer-only test is deleted.
- (b) **No, only the last value hands on** (solution S82): a `return` of a made or moved value is refused in every function, pointer and record alike, with `-> own` or without. The record program above then gets the pointer's error. An early exit with a made value must be rewritten as the last value: `mk := fn (c := i32 ?) -> own @i32 ( if (c == 1) (alloc 1 of i32 3) else (alloc 1 of i32 4) )`.

Recommended: (a), because `-> own` already tells the caller it owes the `free`, whichever line the value leaves by, and Rust works the same: `fn mk(c: bool) -> Box<i32> { if c { return Box::new(3); } Box::new(4) }`. P141 (a `-> void` function's returned value) is not changed by either: that value goes to nobody, and freeing a value nobody takes at its line's end is issue 224's work.

## 2. Who frees a value made inside a call's brackets? (root W269)
**Decision:** for a parameter without `own`, whether the value made for it is freed when the call returns or at the end of the caller's line · **Recommended:** (b) · **Why:** a parameter then owns only when it says `own`, exactly as a result owns only when it says `-> own` (Q89)

---

Two rules disagree about `f := fn (p := @i32 ?) -> i32 ( p@ )` called as `f(alloc 1 of i32 5)`:
- ›Holding is decided at the binding site, parameters included‹: "A constructor result passed straight as an argument, `f(alloc 1 of i32 5)`, is bound to the parameter in the callee's frame, which holds it; no `own` gate is needed, since no caller place is emptied." Your #199 ruling agrees: "f(x + 1) binds a exactly as a := x + 1 does".
- ›Gate spelling: words left of `:=`; ownership in the reference type‹: "a parameter `a := own @T ?` consumes (callee owns, source empties), `a := @T ?` borrows".

The first says `p` owns the value, the second says `p` borrows it. Today the seed refuses the pointer call with the wording of a rule you changed on 30 September ("an owning value must be bound to a name"), and runs the record call `f(box (1, 2))` without ever freeing the box (P4). Both cannot hold at once: the same body serves `f(a)`, where `p` borrows, and `f(alloc …)`, so the body would have to know per call whether to free `p`. That is a hidden flag per call, which you turned down in Q-43 ("i dont think a runtime flag is needed"), or a second copy of the body per way of passing.

- (a) **Freed when the call returns** (solution S83): inside the body `p` borrows in every call, so one body serves all calls, and a value made in the brackets is freed as soon as the call returns, which is where `p`'s life ends. The first rule stays true in effect (the value lives exactly as long as `p`); the second is read as "borrows inside the body". The seed gains one more place where a life ends, the return of a call, in both tiers. Medium-sized.
- (b) **Freed at the end of the caller's line** (solution S84): `p` borrows, as the second rule says, and a value made in the brackets is a value no name takes, so it lives to the end of the caller's line, which frees it (your Q-25 ruling of 30 September: a value nothing takes lives to the end of its line). A function then takes over a value only when its parameter says `own`, as it hands one on only when its result says `-> own`. This replaces the 30 August "parameters included" sentence and narrows #199's "exactly as a := x + 1" for who owns. Nothing new is added: issue 224, which frees a value nobody takes at its line's end, does the freeing. Until issue 224 lands, the refusal stays and also covers a record, so P4 is an error instead of a silent leak. Small.

The two differ only inside one line: in `x := f(box (1, 2)) + g()`, (a) frees the box before `g()` runs and (b) after. `f(box (1, 2)), print «after»` prints `free` then `after` in both.

Recommended: (b), because it adds no new rule and no new place where a life ends, it makes the two ends of a call follow one rule (`own` says who takes over), and Rust does the same with a temporary: `f(&Box::new(5))` drops the box at the end of the statement.

## 3. Where is "this owns its value" written down? (root W271)
**Decision:** whether ownership is recorded in the value's type or on the name, field, parameter or result that holds it, for every type · **Recommended:** (c) · **Why:** on 9 October you asked that these safety facts be thought through carefully before the borrow checker; neither (a) nor (b) is free, and questions 1 and 2 do not need this answer

---

DESIGN.md says it two ways:
- ›Gate spelling: words left of `:=`; ownership in the reference type‹: "Ownership is a word in a reference's type … `own @T` says the reference owns (a fact about the value, like its type)".
- ›A field may be `own t ?`, `t` a type whose body fills `share free`‹: "`own` is a gate on the field's binding, as on an owning name's" (my reading of 25 September, open to you), and ›Three fail-closed ownership rules, and `-> own @T`‹: "`own` as a gate on a reference, the same primitive as `pub`/`mut`".

The seed follows the first for a pointer and the second for a record. `a := alloc 1 of i32 5` gives `a` a new type, "owning `@i32`", made just for owners. `a := bag(3)` keeps the type `bag` and puts an `own` mark on the name `a`. So every check of ownership is written once per kind, or for pointers alone, which is how P143 and P4 came about.

- (a) **In the type, for every type** (solution S85): `own bag` becomes a type of its own, made from `bag` as "owning `@i32`" is made from `@i32`. `a := bag(3)` gives `a` the type `own bag`, and `b := a` gives `b` the type `bag`, a borrow. What changes for a user: an owner's type is `own bag`, not `bag`; and the `free` that `bag`'s body fills runs only for `own bag`, so an array whose cells own their bags must say so, which changes ›A value owns what its elements hold and frees it‹. Large.
- (b) **On the place, for every type** (solution S86): `own` is a mark on a name, field, parameter or result, as `mut` is. `@i32` is one type, and its `free` (giving the memory back) runs only where the place owns. The special "owning `@i32`" type goes. What changes: ›Gate spelling…‹ ("a fact about the value, like its type") and ›`free` runs a value's teardown; only the owning heap pointer has one in core‹; and a pointer in an array's cell has no name to carry the mark, so an array must say whether its cells own what they point to. Large.
- (c) **Not now**: decide it in the talk on ownership you asked for under Q92 (problem P128, how a type's `run` says it hands on a made value). Until then the seed keeps both ways, and the fixes for questions 1 and 2 read ownership through one function that already answers for a pointer and a record alike.

Recommended: (c), because you said on 9 October: "here is where things needs to be thought though realy carefully to get these safety facts correct from the start so that the borrowcheck can be smoothly built ontop", and both (a) and (b) change a rule you ruled and change how arrays say what they own.

## 4. One check for "is this value made", for every type (orchestrator)
**Decision:** whether every place that takes a value asks one function if it is made · **Recommended:** yes · **Why:** one rule in one place; the old pointer-only test is the cause of P143

---

Three places in the seed ask whether a value is made with `is_owning_value`, which knows only pointers: a `return`, a call's argument, and `=` into a pointer that owns. One function, `teardown_of`, already answers for a pointer and a record alike, and the name declaration uses it. The fix has all three ask it and deletes `is_owning_value`.
