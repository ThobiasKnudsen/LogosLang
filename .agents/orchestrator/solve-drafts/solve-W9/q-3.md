## The root cause, in plain words

When the parse meets a call, ›A call is a use of every outer name the callee's body reads‹ says the call must not go ahead if any name the function's body reads from outside has ended. Ended means freed, moved, or out of scope. The rule counts calls too: if `g`'s body calls `climb()`, and `climb` reads `n`, then `g()` after `free n` is refused.

The seed does this by giving every function one list of outside names. When a function's body calls another function, the callee's whole list is copied into the caller's list. In a chain where `h1` calls `h0`, `h2` calls `h1`, and so on, `h2000`'s list holds `c` and `h0` up to `h1999`. Every call then checks every name on the callee's list again, and the copying itself compares each name with every name already on the list. Nothing is kept between two calls, and DESIGN.md has no rule saying what may be kept.

On 9 October you ruled ›Reading a program takes time in step with its size; no walk runs once per path‹: "An answer a walk needs again for the same node is kept, not walked again." But keeping an answer has a catch. It must notice a name that ends between two calls:

```
x := alloc 1 of i32 5, h0 := fn () -> i32 ( x@ ), h1 := fn () -> i32 ( h0() ), print «{h1()}», free x, h1()
```

Today this is refused at the second `h1()` with "`x` is dead here", and the first `h1()` passes. A kept answer must still give that.

## Proof

This program, generated up to `h2000`, reads a chain where each function calls the one before in both arms of an `if`. Nothing is ever called at run time:
```
c := i32 1, h0 := fn () -> i32 ( i32 5 ), h1 := fn () -> i32 ( if (c == 1) (h0()) else (h0()) ), h2 := fn () -> i32 ( if (c == 1) (h1()) else (h1()) ), … , 7
```
On dev 209fd88 it prints `7` after 75 ms with 500 functions, 382 ms with 1,000 and 1,730 ms with 2,000. That is about five times slower for each doubling, where the rule asks for about twice. Without the `if` (one call per body) it is 197 ms with 1,000 and 1,214 ms with 2,000. So the copied lists cost the most, and the `if`'s second call adds to it.

## 1. What may a function keep from checking its outside names, and what makes it check again?
**Decision:** the rule for a function's kept answer · **Recommended:** (a) · **Why:** the chain reads in step with its length, and your decline of a per-name list of readers stays

---

Both options first stop copying lists: a function's list holds only the outside names its own body reads and the functions it calls. A call checks its callee's own names and asks each function the callee calls for that function's answer, and so on down the chain. The refusal above stays, because `h1`'s answer asks `h0`'s, and `h0` reads `x`. This also helps the other question you have open on these bodies (Q87): a body being built no longer needs the full list of every body it calls.

- (a) **Kept until any name ends**: each function keeps the answer of its last check. The parse keeps one count of how many names that some function reads have ended so far. A function checks again only when that count has grown since its last check. The chain above then reads in time in step with its length, because nothing ends between its calls. The cost is one number per function. The worst case is a program that repeatedly ends a name some other function reads and then calls the end of a long chain. It checks the whole chain again each time, so 2,000 ends between 2,000 calls of a 2,000-long chain still costs 2,000 × 2,000.
- (b) **Kept until a name it reads ends**: each name that can end keeps a list of the functions whose bodies read it. When the name ends, those functions are marked as refused, and so are the functions that call them. A call reads one mark. This is in step with the program's size in every case, the worst case too. But it brings back what you declined on 8 September at ›The reader–writer rule is transitive, and resolution is a read‹: "a per-binding list of the declarations using a name", "Rejected, to stay declined". That reason was that such a list answers "who read the name" when the question is "what did the name decide". Here the question really is "who reads this name". Names that never end, such as `i32` or `+`, would get no list.

Recommended: (a), because it fixes the chain your rule names, keeps your decline as it stands, and its worst case needs a program written to hit it.

The words (a) would add under ›A call is a use of every outer name the callee's body reads‹:

> - **Ruled (<the date of your answer>, Thobias):** a function's list holds the outside names its own body reads and the functions its body calls, not theirs. A call checks the names on its callee's list and asks each function on it for that function's own answer. A function keeps the answer of its last check, and checks again only after a name that some function body reads has ended since, by `free`, `move` or the close of its scope. So a chain of 2,000 functions, each calling the one before, reads in time in step with 2,000, and `x := alloc 1 of i32 5, h0 := fn () -> i32 ( x@ ), h1 := fn () -> i32 ( h0() ), print «{h1()}», free x, h1()` still refuses the second `h1()`. **Why:** <your words>.

It replaces "The check is a range lookup per outer name per call" in that rule's Why. That sentence goes to DESIGN_HISTORY.md, with this ruling as the reason.

The words (b) would add under the same rule:

> - **Ruled (<the date of your answer>, Thobias):** as above, except that a function's answer is kept until a name its body reads, or a body it calls reads, ends: each name that can end keeps the list of the functions whose bodies read it, and its end marks them and the functions that call them as refused. **Why:** <your words>.

(b) also changes the Rejected line at ›The reader–writer rule is transitive, and resolution is a read‹ to allow this one list.
