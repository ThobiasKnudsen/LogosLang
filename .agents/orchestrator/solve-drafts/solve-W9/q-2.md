This replaces Q-50, which asked about the same root cause before seven more were added to it.

## The root cause, in plain words

Some bodies are written in one place and built later. A type's `run` body is usually built when the first node of that type appears. A `type (…)` written inside a loop or a function is built each time that body runs. Building a body means parsing its lexed text into graph nodes.

The seed has two functions that build these bodies: `construct_run_body` for a `run` body and `construct_held_type` for a `type (…)` in a body. This is root cause W9. Where a body was written, the seed keeps only its text and its scope. Everything else happens at the build:

1. **The names in the body are looked up at the build**, so a name declared after the body can be seen by it.
2. **A body that needs another body builds that one inside its own build.** If `t0`'s `run` body contains a node of type `t1`, then building `t0`'s body builds `t1`'s body in the middle, and so on down a chain. Every link stays on one Rust call stack.

Proof of 1, on dev 83e3f97 (interpreted). The `run` body of `u` declares its own `z`. The program declares another `z` after `u`:
```
u := type ( a := ?, output_type := type ?, share run = ( z := a, f64(z) ), share parse_rank = 60, share parse = ( tape[0]:type = u, tape[0].a = tape[1], tape[0].output_type = f64, tape.remove(1), tape.is_constructed[0] = true ) ), z := i32 0, x := i32 3, print «{u x}»
```
This prints `error: z is already declared and still in scope` and exits with 1. Without `z := i32 0, ` it prints `3.0`. This is P6 (issue #230). P38 is the same thing through a `type (…)` in a loop.

Proof of 2: P23 is a chain of 18 types. Each type's `run` body is 1,990 brackets deep around a node of the next type:
```
t1 := type ( a := i32 ?, share run = ( ((( … 1,990 deep … 3 t2 … ))) ), share parse_rank = *.parse_rank + 1, share parse = ( … ) ), … , 3 t0
```
With 17 links it prints `leaf`. With 18 links the program dies with `thread has overflowed its stack` (SIGABRT), not with a Logos error. I ran it again today: it dies the same way when the field is `a := ?` instead of `a := i32 ?`.

## What the problem graph says

```
W9    a body written early is built later, and keeps only its text and scope
├─ names looked up at the build ── W10, W202 ──────────────→ P6, P38 (#230)
└─ a body built inside a body ── W130, W177, W192, W183 ──→ P23
      and nothing counts the depth across builds ── W138, W168 ──→ P23
```

The root causes in that picture, each in one sentence:

- **W10**: the lookup keeps a name whose scope is open and that is not freed, and never asks whether the name was declared before the body.
- **W202**: DESIGN.md stores a name's life as two pointers into the body, so asking "was this name alive at that earlier point?" means walking the body, which the seed never does.
- **W130**: a `run` body over typed fields is never built at its definition, though ›A generic function body is lexed once and built once per set of field types‹ says it should be.
- **W177**: ›A call is a use of every outer name the callee's body reads‹ needs the inner body's list of outer names, and the seed only has that list after building the inner body.
- **W192**: the type a node gives back is only worked out as part of building its body.
- **W183**: DESIGN.md does not say what a node of a type with a `run` gives when the type has no `output_type`.
- **W138**: DESIGN.md has no rule on how deep nesting may go. The seed's limit of 2,000 brackets restarts at 0 inside every body built later, so a chain never reaches it.
- **W168**: the rule ›A constructor's outcome is read off its own cell; no holding, no re-invocation‹ means a constructor cannot stop at an inner bracket and continue later. That is why nesting has to use the Rust stack.

Related root causes that this does not decide: W12 (five separate readers of a scope's lines, solution S9 on #234) and W75 (one function both runs a scope's lines and closes the scope). Both rest on the same rule, ›The pass runs only as far as it must, in order, and never twice‹.

## 1. Where does a body that is built later read its names?
**Decision:** which line a later-built body's names belong to · **Recommended:** (a) · **Why:** DESIGN.md already reads names this way for function calls

---

P115 (a problem found while tracing P23) shows that DESIGN.md says two things here. ›A binding's fields are read at elaboration, at the line of the read‹ says a read is answered "when the node holding the read is built, from the binding as it stands at that line". For a body built later, that is the build. Its Why says "A reader at an earlier line must not see a later state, so the answer is fixed where the read is built". That reads as where the body is written. ›A call is a use of every outer name the callee's body reads‹ says "A body resolves outside names when parsed … the body's `n` is the old, ended name. To read the new name, declare the function again after it."

Example where the two readings differ: `x := i32 5, t := type ( a := i32 ?, share run = ( x + a ), … ), free x, x := f64 1, 3 t`. Read where written, the body's `x` is the first `x`, which is freed, so `3 t` is the dead-name error. Read where built, it is the new `f64` `x`.

- (a) **Where it is written (S49)**: a body built later looks up every name where it is written, once, as part of the part of it built there. Its build never looks up a name again. P6 and P38 print what they print without the later `z`. The question "was this name alive at an earlier point?" is then never asked while parsing, so W202 needs no change now.
- (b) **Where it is built, filtered by where it was written (S50)**: each line of a body gets a number, a name's life becomes two numbers, and every lookup checks that the name's life covers the place the body was written. This also fixes P6 and P38. In the example above, `3 t` reads the new `x`, which goes against "the body's `n` is the old, ended name".

Recommended: (a), because it is what ›A call is a use…‹ already says, and the build then has nothing left to look up.

The words (a) would add under ›A binding's fields are read at elaboration, at the line of the read; running code never reads a binding‹:

> - **Ruled (8 October 2026, Thobias, W9, P115):** a body written in one place and built in another, a `fn` body, a type's `run` body or a `type (…)` in a body, reads every name and every binding field as it stood where the body is written, and its build looks up no name again: `u := type ( a := ?, …, share run = ( z := a, f64(z) ), … ), z := i32 0, x := i32 3, print «{u x}»` prints `3.0`, since the later `z` did not exist where the `run` body is written. **Why:** <your words>.

## 2. What does a node of a type with a `run` give when the type declares no `output_type`?
**Decision:** what such a node gives back · **Recommended:** (a) · **Why:** it is known without building the body, which question 3 needs

---

In P23 every `t1`, `t2`, … has a `run` but no `output_type`. DESIGN.md does not say what `3 t1` gives back. Today the seed gives nothing, and P23's last line prints `0`. On 2 October (Q-59, Q-61) you ruled that `:=`, `return`, `while` and the other statement words have no `output_type` and give their line nothing.

- (a) **Nothing (S54)**: a type gives a value only when it says what that value is, with `output_type`. Over such a type `t`, `y := 3 t` is the error "this gives nothing". The parse knows this as soon as it places the node, without building the body.
- (b) **What its `run` body's last line gives (S55)**: this is how you ruled on 8 October (Q72) that a block's value is worked out. But the type of the last line is only known after the body is built for this node, so every such node used as a value forces a build inside the build that uses it. That is exactly P23's nesting.

Recommended: (a), because it is the statement-word rule applied to every type, and it is what lets question 3's fix place a node before its body is built.

The words (a) would add under ›A node's output type is per node, and its parse writes it‹:

> - **Ruled (8 October 2026, Thobias, W183):** a node of a type with a `run` gives nothing when its type declares no `output_type`, as the statement words do; over such a type `t`, `y := 3 t` is the error of binding nothing. **Why:** <your words>.

## 3. How should a chain of bodies that build each other behave (P23)?
**Decision:** how P23 is fixed · **Recommended:** (a) · **Why:** the chain runs, and a deep wall of brackets still gets a Logos error

---

- (a) **Build after, not inside (S51), with a depth rule as a safety net (S52)**: when a body being built places a node of a type whose `run` body is not built yet, the node is placed straight away. Its output type comes from question 2, and its list of outer names comes from question 1. Its body goes on a list and is built as soon as the build that placed it ends, still before anything runs. The chain in P23 then runs at any length. Separately, the 2,000-bracket limit gets a rule and counts across bodies too. An error inside `t1`'s body then shows up just after `t0`'s body is built, not in the middle of it. This needs (a) in question 1 and (a) in question 2.
- (b) **Only the depth rule (S52)**: brackets are counted across every body being built. P23 at 18 links gives the Logos error "scopes nested deeper than 2000" instead of crashing, but it still cannot run. This is small, about 30 lines.
- (c) **Nesting in memory instead of on the Rust stack (S53)**: a constructor may stop at an inner bracket and continue at its closing bracket, so depth is limited only by memory. This changes ›A constructor's outcome is read off its own cell; no holding, no re-invocation‹ and rewrites the driver and every constructor. That is far more than this needs.

Recommended: (a), because nothing builds inside a build any more, and the depth rule still turns a 2,500-deep bracket wall into an error instead of a crash.

The words (a) would add. Under ›A generic function body is lexed once and built once per set of field types‹:

> - **Ruled (8 October 2026, Thobias, W130, W177, W192):** a body that waits for a node is built after the build that placed the node ends, never inside it. The node is placed first, with its output type and the outer names its body reads, both known before that body is built. **Why:** <your words>.

Under ›The scope's constructor is the driver‹:

> - **Ruled (8 October 2026, Thobias, W138):** the drive's nesting has a limit, set by the implementation (the seed's is 2,000). Crossing it is a checked error at the bracket that crosses it, never a crash. The count is every bracket open in the whole pass at that moment, inside a body being built too. **Why:** <your words>.

## 4. Drop the two "keep one build per set of values" solutions?
**Decision:** S28 and S29 rejected or kept · **Recommended:** (a) · **Why:** your Q-44 and Q-46 answers rule them out

---

S28 and S29 were the first solutions for W9. Both kept one build of a `type (…)` in a body for each set of values it reads, so `mk(i32) == mk(i32)` would be `true`. On 1 October you ruled the opposite: "there is nothing defined to do minting of anything a function runs" (Q-44), and a `type (…)` in a loop is a new type each time round (Q-46).

- (a) **Reject both**, with those words as the reason.
- (b) **Keep them proposed**, in case an explicit "mint on these values" form comes later.

Recommended: (a), because an explicit form would be a new solution with your own words.
