## 1. Give each rule one home, chosen by who reads it (orchestrator)
**Decision:** how to fix nine root causes about rules that stand in the wrong file or in two files · **Recommended:** (a) S46 · **Why:** it is the only option that removes the cause; the others patch two sentences or bring copies back

---

**What this is about.** Three files hold the rules that agents follow.

- `~/.claude/CLAUDE.md` is your global instruction file. Every Claude session on this machine reads it, also sessions in repos with no orchestrator.
- `~/.claude/skills/orchestrate/agent-agnostic-prompt.md` holds "the rules every agent follows in every repo". Your CLAUDE.md imports it (line 71), so every session reads it too. The orchestrator also pastes it into every prompt it gives an agent.
- `~/.claude/skills/orchestrate/every-prompt.md` holds the rules for agents that an orchestrator starts. Only those agents get it. It has blanks such as `{{ORCH}}`, which the script fills in with the repo's names.

**The root cause, W101.** (A "W" is a cause in the problem graph, `PWS.json`, that explains one or more problems; a "P" is a problem; an "S" is a proposed solution.) agent-agnostic-prompt.md is meant for every session, but it is written in the orchestrator's own words. It says "report a problem as FOUND and never file it" and "only the orchestrator writes the ruling document". A session in a repo with no orchestrator has nobody to send FOUND to. And your CLAUDE.md tells that same session the opposite. This is problem P88:

```
agent-agnostic-prompt.md:12  A problem your task does not cover is reported as `FOUND` and never filed.
CLAUDE.md:88                 In a repo without an orchestrator, a root cause is filed as an issue with the `root-cause` label
```

There should be one rule per case. Problem P95 is the same clash about who records a ruling: CLAUDE.md says "record it yourself, in KNOWLEDGE.md", and agent-agnostic-prompt.md says "only the orchestrator writes the ruling document".

**Eight more root causes are alike,** so the orchestrator gave them to me, and one fix serves all nine:

- W102: CLAUDE.md keeps its own copies of three rules the import already holds: write every change as if it ships to production, stop and ask after two or three failed attempts, and never read secret files.
- W106: no sentence says which file wins when two disagree. So every exception for the orchestrator gets written into CLAUDE.md, beside the general rule it overrides.
- W108 and W193: SKILL.md, the orchestrator's own rule file, says "a ruling on how the orchestrator works is recorded in this skill" twice (line 10 and line 70). Its other rules about its own files are spread over three sections.
- W116: CLAUDE.md sends an unsettled decision to mem0 and a waiting rule wording to auto-memory. Question 2 below is about this one.
- W184: SKILL.md expects each repo's ruling document to point to the skill for rulings about the orchestrator, and none does.
- W189 and W194: how to write down a ruling (a Ruled line with the date, who and the reason; the old text to a history file) is written out in five files. The template for a ruling document states it at the top, but agents are told to read that document only from one `###` heading to the next, so nobody reads the top. A repo with no orchestrator may have no such document at all. And CLAUDE.md names the file KNOWLEDGE.md, while LogosLang's ruling document is DESIGN.md (problem P94).

Together the nine explain five problems: P74 (eight rules stand in two or three places at once), P88, P94, P95 and P96.

**The options,** as recorded in the graph:

- (a) **S46: one home per rule, by who reads it.**
  - agent-agnostic-prompt.md keeps only the rules that hold with or without an orchestrator. Where the two cases differ, the one rule names both. For example: "A problem your task does not cover: under an orchestrator, report it the way its prompt says; where none runs, file it as an issue with the `root-cause` label."
  - It also gets the one way to record a ruling, for everyone: a Ruled line at the rule it touches, the old text in the history file beside the ruling document, and a decision that must wait as a Pending line at that rule. It names "the repo's ruling document", never a file name.
  - It gets one sentence on which file wins: the narrower one. A repo's AGENTS.md wins for that repo, then the orchestrator's prompts and skill for its agents, then agent-agnostic-prompt.md, then your CLAUDE.md.
  - every-prompt.md keeps the orchestrator's protocol (FOUND, ANSWER, who writes the ruling document).
  - Your CLAUDE.md keeps your personal way of working (Core Behavior, Musk's rules, the Behaviour rules, the GoT steps, the git SSH keys, the MCP security bullets) and the import line. It loses the copies, the hand-kept list of the import's topics, and its sentences meant only for the orchestrator.
  - SKILL.md gets one short section on its own files, and its other rules point to it.
  - Your own sessions behave as before, except for what question 2 decides. It is text only, a few hours of work, done by the orchestrator.
- (b) **S47: patch the two clashing sentences.** Only lines 9 and 12 of agent-agnostic-prompt.md get "under an orchestrator ..., without one ...". This fixes P88 and P95 and nothing else. The other eight root causes, and P74, P94 and P96, stay.
- (c) **S48: stop importing agent-agnostic-prompt.md into CLAUDE.md,** and merge it into every-prompt.md. The clashes go away. But then the faithfulness, comment and file rules would stand twice, once in CLAUDE.md for your own sessions and once in every-prompt.md for the agents. Ending exactly that was why you made agent-agnostic-prompt.md on 5 October 2026. The other choice is that your own sessions lose those rules.

Why (a) still keeps two shared files: agent-agnostic-prompt.md is imported as it is into every session, so it cannot hold blanks like `{{ORCH}}`. every-prompt.md needs those blanks. So each rule gets one of the two as its home, never both.

Recommended: (a), because it is the only option that removes the cause: each rule then stands once, in the file meant for its reader. The recorded rules decide this (a root fix over a patch, one place for a rule), so it is the orchestrator's to decide.

## 2. Where a decision waits until it is settled, in every session
**Decision:** whether your own sessions stop putting rulings and unsettled decisions in mem0 and auto-memory · **Recommended:** (a) · **Why:** mem0 is not connected, and auto-memory is seen only by sessions started in one folder on this machine

---

Today your CLAUDE.md says two things about a decision that is not settled yet:

- Under `## Code Changes`: "Probable decisions can still be stored in mem0 for future reference even before confirmation".
- Under `## Rulings and their records`: a ruling whose wording must wait goes "as an explicit pending edit in auto-memory".

The GoT steps also ask: "Does this conflict with mem0 memories?"

No mem0 server is connected on this machine. `claude mcp list` on 8 October 2026 lists Claude Docs, Gmail, Google Drive, Outline, linear and a few others, and no mem0. So those decisions are stored nowhere (problem P96). Auto-memory is read only by sessions started in that same folder on this machine; the team, the agents and other orchestrators never see it. You barred the orchestrator from it for that reason on 5 October 2026 (Q-thobias-111). The orchestrator writes a Pending line instead: a line at the rule it touches, in the repo's ruling document, with the date, your words and what it waits for. For example, under a rule in DESIGN.md:

```
- **Pending (<date>, Thobias, <question>):** <your words>; waits for <what must be settled first>.
```

It becomes a Ruled line when the wait ends.

- (a) **A Pending line in every session.** Every session, with or without an orchestrator, writes an unsettled decision or a waiting wording as a Pending line at the rule it touches, in the repo's ruling document (or in SKILL.md, for a rule of the orchestrator skill). mem0 leaves your CLAUDE.md. The GoT check becomes "Does this conflict with the ruling document, or with a Pending line in it?". Auto-memory stays for what it holds about you and how you like to work; only rulings and waiting decisions stop going there. Nothing already in auto-memory is moved or deleted.
- (b) **Keep today's homes for sessions without an orchestrator.** mem0 and auto-memory stay in CLAUDE.md, with the orchestrator's exception beside them. P96 stays: those decisions are stored nowhere until a mem0 server is connected.

Recommended: (a), because a decision kept where no other session reads it, or in a server that does not exist, is a decision lost. It also removes the orchestrator's exception, so one rule holds for every session.
